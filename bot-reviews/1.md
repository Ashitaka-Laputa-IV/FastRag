# FastRag 代码审阅（第 1 轮）

- 审阅对象：`12edf0d`（Merge PR #8 `feat/rag-graph`），`main` 分支，工作区干净
- 代码规模：9 个 Python 模块 / 1200 行、7 份 TOML、3 份 prompt、1 份 13 行 README
- 审阅方式：全量静态阅读 + 本地实测（切块偏移不变式、BM25 召回的边界行为、RRF 边界、索引加载耗时、三方库签名核对）
- 未覆盖：真实 API 调用（不消耗 key），因此 LLM 链路与向量召回的实际质量只做代码级推断

## 1. 总体结论

作为**早期 demo**，这个项目的完成度是合格偏好的：

- 分阶段可运行、可复现：`下载 -> 切块 -> 向量化 -> BM25 -> RRF/重排 -> 图编排`，每一步都有独立入口和 docstring
- 配置外置、提示词外置、`data/` 与 `.env` 已正确 gitignore，`uv.lock` 已提交
- 切块阶段的 `text == 原文[start:end]` 不变式经实测成立，`id` 全局唯一
- 图编排（LangGraph）与检索（bm25s + numpy 手写余弦）之间解耦得比较干净，`Pipeline` 用闭包注入依赖，节点函数易读

但**距离可维护的工程代码还有明确差距**，主要问题集中在四类：

1. **配置双源**：同一组参数在 2~3 份 TOML 里各写一遍，图实际只读 `rag.toml`，其余配置项在图里静默失效 —— 改配置不生效是最难排查的一类 bug
2. **产物之间没有版本约束**：`chunks.jsonl`、`vectors.npy`、`bm25-index/` 三者只靠"行序"和"id"隐式对齐，任一阶段重跑后另一阶段不变就会静默错位（这是 RAG 项目最经典的静默错误）
3. **图的分支逻辑有实质缺陷**：判定"不需要检索"后仍然走 RAG 答案 prompt，导致闲聊类问题被回答成"资料不足"；BM25 的 0 分结果会以 rank 1 的身份进入 RRF，把垃圾文档顶到前面
4. **重复代码**：`load_env` ×3、`load_chunks` ×2、`format_snippet` ×2、`ROOT` ×5、配置 dataclass ×5、检索编排 ×2

| 维度 | 评分 | 说明 |
| --- | --- | --- |
| 可读性 | 4/5 | 命名清晰、docstring 到位、无死代码；中文注释风格统一 |
| 一致性 | 2/5 | 配置多处重复、错误处理方式不统一、state 内 dict 形态不一致 |
| 正确性 | 2/5 | 见 P0-2/P0-3/P0-4，均可静默产生错误结果 |
| 健壮性 | 2/5 | 空输入/网络异常/中断都未处理，`SystemExit` 混用在库层 |
| 可测试性 | 2/5 | 纯函数不少但 0 测试、0 CI、无 lint 配置 |
| 工程化 | 2/5 | console script 指向 stub，wheel 安装后找不到 config/prompts |

**结论**：适合作为学习/demo 保留；若要作为后续项目基础，建议先完成 P0（4 项）与 P1 中的"配置归一 + 产物校验"，再谈加功能。

问题统计：P0 4 项、P1 8 项、P2 20 项、P3 6 项。

## 2. P0：会产生错误结果或直接不可用

### P0-1 资源路径依赖源码树，console script 指向占位实现

位置：`rag_graph.py:53-55`、`chunk_docs.py:26-27`、`embed_chunks.py:37-39`、`keyword_search.py:21-22`、`llm.py:25-27`、`reranker.py:30-32`、`rrf.py:41-42`、`pyproject.toml:22`、`__init__.py:1-2`

每个模块都用同一段代码定位仓库根：

```python
ROOT = pathlib.Path(__file__).resolve().parent.parent.parent
CONFIG_PATH = ROOT / "config" / "..." 
```

只有在"源码目录 + editable 安装"（`uv run python -m fastrag.x`）时成立。一旦 `uv build` 后安装 wheel：

- 包内只有 `src/fastrag/**`，`config/` 与 `prompts/` 不在包内（`uv_build` 不会收仓库根目录的裸目录）
- `ROOT` 会解析成 `site-packages/`，所有 `load_config()` 直接 `FileNotFoundError`
- 目前 `uv sync` 之所以能跑，是因为 uv 默认把本项目装成 editable，`__file__` 仍指向 `src/`

同时 `pyproject.toml:22` 的入口：

```toml
[project.scripts]
fastrag = "fastrag:main"
```

指向 `__init__.py:1-2` 的 `print("Hello from fastrag!")`，即 `uv run fastrag` 只会打印问候语，与整套流水线无关；真正的入口分散在 8 个 `python -m fastrag.xxx` 里。

建议：

- `config/`、`prompts/` 移入 `src/fastrag/resources/`，用 `importlib.resources.files("fastrag.resources")` 读取，或至少支持 `FASTRAG_HOME` 环境变量覆盖
- 入口改为单一 CLI（`fastrag/cli.py` + argparse 子命令：`download/chunk/embed/index/ask`），`[project.scripts] fastrag = "fastrag.cli:main"`
- `[project]` 补 `license`（仓库里已有 MIT LICENSE 但 pyproject 未声明）

### P0-2 判定"不需要检索"后仍走 RAG 答案 prompt

位置：`rag_graph.py:221-223`、`rag_graph.py:181-194`、`prompts/answer.txt:1`

```python
@staticmethod
def route_after_decide(state):
    return "requery" if state.get("need_search", True) else "answer"
```

跳过检索直接进 `answer` 节点，而 `answer` 无论有没有检索结果都用同一个模板：

```python
context = (... or "（无检索结果）")
prompt = self.prompts["answer"].format(context=context, question=state["question"])
```

`prompts/answer.txt` 第一句是"请依据下面的资料回答问题，资料不足时直接说明，不要编造"。于是用户问"你好""你是谁"，模型会回答"资料不足"。这条分支等于把功能做坏了，也让 `decide_search` 节点（一次额外 LLM 往返）几乎只有负收益。

建议（二选一）：

```python
def answer(self, state):
    if not state.get("need_search", True):
        return {"answer": self.llm.invoke(state["question"]).text.strip()}
    ...
```

或者直接删掉 `decide_search` 节点：本项目的检索成本只有几十毫秒（见 §4 实测），而一次 LLM 判定要 ~1s，检索永远做反而更快更稳。若保留，建议与 `requery` 合并成一次结构化输出（`{need_search, query}`），省一次往返。

### P0-3 三份产物之间没有版本校验，重跑任一阶段即静默错位

位置：`embed_chunks.py:154-166`、`keyword_search.py:56-69`、`keyword_search.py:72-82`

向量的复用条件只比较三个字段：

```python
if (manifest["model"] == config.model
        and manifest["dimensions"] == config.dimensions
        and manifest["count"] == len(chunks)):
```

`manifest.json` 里虽然记了 `chunks_file` 路径和 `created_at`，但**没记内容指纹**。于是：

- 改 `chunk_size`/`chunk_overlap` 重跑 `chunk_docs`，若 chunk 总数恰好不变（或用户改的是纯文本内容），`count` 仍相等 → 复用旧向量。`vectors[i]` 与 `chunks[i]` 从此错位，检索结果看起来"能跑"，但返回的文本和分数无关
- BM25 侧更彻底：`build_index` 不写任何参数/指纹，`search` 不做任何校验。改了 `method`/`stopwords` 后不重建索引，配置静默失效（`bm25s.BM25.load` 恢复的是构建时的参数）
- 若重跑了 `chunk_docs` 但忘记 `keyword_search build`，BM25 的 corpus 与 `self.chunks` 变成两套不同的语料。`Pipeline._merge` 和 `rrf_fuse` 都按 `id` 合并，于是两套语料的文档会静默混入同一份结果

建议：

1. `manifest.json` 与 `bm25-index/meta.json` 都记录 `chunks_sha256`（或 `mtime+size`）+ 构建参数（tokenizer/chunk_size/overlap；method/stopwords）
2. 加载前校验，不匹配时明确报错："chunks.jsonl 已变更，请重新运行 `fastrag embed` / `fastrag index`"
3. 把"chunk -> embed/index"串成一个 `fastrag prepare` 命令，避免手工漏步

### P0-4 BM25 的 0 分结果被当成真实命中，且以 rank 1 进入 RRF

位置：`keyword_search.py:79-82`、`rrf.py:83-87`

`bm25s.retrieve` 在"查询词全部不在词表"时**不返回空列表**，而是返回 k 篇分数为 0 的任意文档。实测：

| 查询 | 得分 | 结果 |
| --- | --- | --- |
| `langgraph human in the loop` | 4.122 / 4.077 / 4.021 | 合理命中 `human-in-the-loop.md` 等 |
| `如何使用智能体` | 0.0 / 0.0 / 0.0 | `common-errors.md#0-2004`、`acp.md#5106-7111`、`acp.md#3436-5536`（与查询无关，且每次都一样） |
| `什么是检索增强生成` | 0.0 / 0.0 / 0.0 | 同上三篇 |

`fuse` 的 RRF 分支把排名直接交给 `rrf_fuse`，而 RRF 只看名次不看原始分数：

- 0 分垃圾文档拿到 `1/(60+1) = 0.01639`
- 真实向量命中排第 5 只拿到 `1/(60+5) = 0.01538`

**垃圾文档稳定压过真实的向量召回**，且由于每次都返回同三篇，结果是系统性偏差，不是随机噪声。

建议在 `keyword_search.search` 内过滤：

```python
return [(float(score), chunk) for score, chunk in zip(scores[0], results[0]) if score > 0]
```

同理，向量侧也建议加一个 `min_score`（余弦 0.3~0.45）兜底，并在 `fuse` 里对空候选提前返回（见 P1-4）。

## 3. P1：明显影响质量/可维护性

### P1-1 中文查询在 BM25 路上基本无效

位置：`prompts/requery.txt`、`config/search.toml:6`、`llm.py:28`、`rag_graph.py:14-19`

`config/search.toml` 用 `stopwords = "english"`，`bm25s` 的切词是"按非字母数字切 + 英文停用词"，CJK 没有分词，整句中文会变成一个 OOV token：

- `如何使用 LangGraph` → 0.863（只靠 `LangGraph` 这一个英文词命中）
- `如何实现人工审批` → 0.0（全 0）
- `langgraph human in the loop` → 4.122

而项目的演示问题、docstring 示例都是中文（`llm.py:28`、`rag_graph.py:15`、`reranker.py:11`），`prompts/requery.txt` 又没有约束输出语言。结果是：中文提问时 BM25 要么全 0、要么极低分，双路召回退化成单路。

建议：

1. `requery` 明确要求输出"英文关键词 + 保留原始实体词"，例如"输出用于英文技术文档检索的关键词串，保留 API 名与代码标识符"。这是**成本最低**的修法，且对向量侧也有利
2. 或对 BM25 侧单独做英文改写（可以让 `requery` 输出 `{vector_query, keyword_query}` 两个字段）
3. 若要支持中文原文检索，则需要引入分词（jieba）或在入库前对文本做中文处理 —— 但本语料是全英文文档，方案 1 更合适

### P1-2 配置双源：同一参数写 2~3 遍，且在图里只有一份生效

| 参数 | 定义位置 | 图里是否生效 |
| --- | --- | --- |
| `candidates` | `rag.toml:5`、`rrf.toml:6`、`reranker.toml:11` | 仅 `rag.toml` |
| `fusion.k` | `rag.toml:9`、`rrf.toml:4` | 仅 `rag.toml`（`rrf.toml` 只被 `rrf.main()` 用） |
| `fusion.weights` | `rag.toml:10`、`rrf.toml:5` | 仅 `rag.toml` |
| `top_n` | `rrf.toml:7`、`reranker.toml:12` | 仅 `reranker.toml` |
| `search.k` | `search.toml:10`、`embedding.toml:19` | 否（图用 `candidates`） |

当前数值恰好一致（`candidates=20`、`k=60`、`weights=[1,1]`），所以问题还没暴露；一旦有人只改 `rrf.toml` 里的 `k`，图的行为不会变，排查成本极高。

建议：只保留一份 `config/app.toml`（或 `config/default.toml` + `config/local.toml` 覆盖），用 pydantic + `pydantic-settings`（pydantic 已是 langchain 的传递依赖）做一次解析、一次校验，各模块只接收配置对象，不再各自 `tomllib.loads`。

### P1-3 重排分支的三处不一致

位置：`rag_graph.py:169-179`、`rag_graph.py:183`、`config/reranker.toml:12`

```python
merged = self._merge(bm25, vector)
documents = rerank_chunks(self.reranker, state["question"], merged)   # 用原问题
return {"fused": [self._to_chunk(d) for d in documents]}
```

1. 检索用 `search_query`（LLM 改写后），重排用 `state["question"]`（原始问题）。cross-encoder 用原始自然语言问题其实未必是错的，但这是**未记录的行为差异**，与 RRF 分支的口径不一致，后续改动极易踩坑
2. 重排分支不按 `context_n` 截断，实际条数由 `config/reranker.toml:12 top_n=5` 决定；`answer` 里又用 `context_n=5` 截一次。若把 `rag.toml` 的 `context_n` 调到 8，rerank 模式下只能拿到 5 条，且**不会报错**
3. `self.reranker` 在 `method == "rrf"` 时是 `None`（`rag_graph.py:130-134`），但没有类型标注，也没有在 `fuse` 里断言非空

建议：`top_n` 只保留一份（融合层统一按 `context_n` 截断，把 `top_n` 传给 reranker 时用 `context_n`），并在 `rerank_chunks` 的 docstring 里写明"重排使用原始问题"这一决策。

### P1-4 候选为空时重排会打一个空请求

位置：`rag_graph.py:173-176`、`reranker.py:87-104`

`_merge` 可能返回空列表（语料为空、或按 P0-4 加了分数过滤后全部被滤掉）。此时 `HttpReranker.rerank` 会 `POST {"documents": []}`，服务端大概率 400，异常直接冒泡终止进程。

建议：

```python
if not merged:
    return {"fused": []}
```

### P1-5 每轮提问都从磁盘重建检索资源

位置：`keyword_search.py:77`、`embed_chunks.py:193`

- `search_keywords` 每次调用都 `bm25s.BM25.load(..., load_corpus=True)`：实测 17~33ms/次，同时把 2625 条 corpus（含全文）再读一份进内存
- `search_vectors` 每次调用都 `build_embeddings(config)` 新建 `OpenAIEmbeddings`（含 key 校验与 httpx client 构造）

在当前规模下能跑，但：检索随语料线性变慢，且图里两个召回节点是并发执行的（LangGraph 同步节点走线程池），会同时做重复 IO。`Pipeline` 已经缓存了 `self.chunks`/`self.vectors`，却唯独没缓存 retriever 和 embeddings client，属于遗漏。

建议在 `Pipeline.__init__` 里建一次：`self.retriever = load_retriever(...)`、`self.embeddings = build_embeddings(...)`，并把 `search_keywords`/`search_vectors` 拆成"接收客户端"的版本。

### P1-6 交互循环没有任何错误处理

位置：`rag_graph.py:265-287`

一圈网络调用（3 次 LLM + 1 次 embedding + 1 次 rerank）任一失败，异常直接冒出 `while` 循环，进程退出；Ctrl-C 在流式输出中也没有捕获。对交互式 CLI 来说，一次瞬时 5xx 就丢掉整个会话。

另外重排器**没有重试**：`langchain_reranker` 内部是单次 `httpx.post`，而 embeddings 有 `max_retries=3`、chat model 有 SDK 默认重试 —— 三条链路的重试策略不一致。

建议：

- 每轮包 `try/except Exception`，打印一行错误后继续等下一个问题
- rerank 失败时降级为 RRF（`except` 里直接走 `rrf_fuse`），比直接崩掉更符合 RAG 的"可用性优先"
- 捕获 `KeyboardInterrupt` 时区分"中断本轮"与"退出"

### P1-7 零测试

纯函数、易测且价值高的点很多，却一条测试都没有：

| 目标 | 测试内容 |
| --- | --- |
| `rrf.rrf_fuse` | 双路累加、单路命中、权重、空输入、重复 id |
| `chunk_docs` | `text == 原文[start:end]`、id 唯一、空目录 |
| `rag_graph.Pipeline._merge` | 去重与顺序 |
| `load_env` | 引号、注释、`setdefault` 不覆盖 |
| `Pipeline`（图） | fake LLM + fake retriever，验证 `need_search` 两条分支 |

建议加 `[dependency-groups] dev = ["pytest", "ruff"]`，并把 `data/` 换成 3~5 篇的小 fixture，保证测试不需要网络与 2.6k 语料。

### P1-8 有 lint 约定但没有 lint 工具

`download_example_docs.py:39,87` 写了 `# noqa: BLE001`，说明作者按 ruff 的规则在写，但 `pyproject.toml` 里既没有 `ruff` 依赖也没有 `[tool.ruff]`；仓库无 CI、无 pre-commit。约定无法被强制执行，下一个贡献者会破坏它。

建议：`dev` 组加 `ruff`，写 `[tool.ruff]`（`line-length = 100` 与现有代码一致、`select = ["E","F","I","UP","B","SIM"]`），再加一个最小 GitHub Actions（`ruff check` + `pytest`）。

## 6. 架构改进建议

### 6.1 收敛成 `Retriever` 协议，消除三处重复编排

现状是"每个 CLI 各拼一遍 BM25 + 向量 + 融合"。建议：

```python
# fastrag/retrieval/base.py
class Retriever(Protocol):
    def retrieve(self, query: str, k: int) -> list[tuple[float, dict]]: ...

class BM25Retriever:      # 持有已加载的 retriever，不再每次 load
    def retrieve(...)
class VectorRetriever:    # 持有 vectors + embeddings client
    def retrieve(...)
```

`Pipeline`、`rrf.main()`、`reranker.main()` 都只依赖协议，融合策略（rrf / rerank）也做成实现同一协议的策略对象。这样 `rag_graph` 就只剩图本身，`rrf.py` 里那 30 行编排代码可以删掉。

### 6.2 配置单一来源

```python
# fastrag/settings.py
class Settings(BaseSettings):        # pydantic-settings
    model_config = SettingsConfigDict(toml_file="config/app.toml", env_prefix="FASTRAG_")
    llm: LLMConfig
    embedding: EmbeddingConfig
    retrieval: RetrievalConfig       # candidates / top_n / context_n
    fusion: FusionConfig             # method / k / weights
    bm25: BM25Config
```

关键是**每个参数全项目只出现一次**；现在的 `candidates` 三处、`k` 两处、`top_n` 两处必须收敛。

### 6.3 产物版本链

```
chunks.jsonl  --sha256-->  embeddings/manifest.json
              --sha256-->  bm25-index/meta.json
```

加载时三向校验，不一致就报错并提示具体命令。这一条能消灭本项目最难排查的一类问题（"为什么检索结果和文档对不上"）。

### 6.4 统一的错误与日志

- `FastragError(Exception)` 作为库层唯一出口，CLI 捕获后转 `exit(1)`
- 所有 `print` 改成 `logging`（`--verbose` 控制 INFO/DEBUG），只在 CLI 层 `print` 用户可见内容
- 每条链路（LLM/embedding/rerank）统一重试与超时配置

### 6.5 加一个 20 条的评估集

`eval/questions.jsonl`（问题 + 期望命中的 `source`），跑 `recall@5`、`MRR`，对比 `rrf` vs `rerank`、`chunk_size` 512 vs 256、`candidates` 20 vs 40。没有这个，"调参"只能靠感觉；有了它，P0-4、P1-1 这类问题的收益也能被量化。
