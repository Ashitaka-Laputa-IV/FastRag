# RAG 各阶段耗时基准报告（RRF 配置）

> 历史报告：以下数据采集于合并 `upstream/dev` 之前（`338d247`），保留原样便于对照。
> 合并后的配置差异与复测数据见 [`bench-data-changes.md`](bench-data-changes.md)。

- 日期：2026-10-26
- 分支：`bench`（基于 `upstream/dev`，基线 `12edf0d`）
- 当前配置：`config/rag.toml` 的 `fusion.method = "rrf"`（由上一版 `rerank` 切换）
- 脚本：`src/fastrag/bench.py`
- 原始明细：`data/bench/results.json`（`data/` 已被忽略，不随仓库提交）
- 测量方式：3 个问题 × 每题 3 次，另加 1 次预热（不计入统计）

## 1. 摘要

- 9 次运行端到端中位数为 **22.0 s**（均值 21.9 s，范围 12.6–30.8 s）。
- 融合（本地 RRF）中位数 **0.1 ms**，占端到端 **0.0%**；单独跑 1000 次测得每次 **0.010 ms**。
- 成本仍集中在远程模型调用：**生成约 64%**，路由约 20%，问题重写约 16%，召回约 0.8%。
- 与切换前的 rerank 基线相比，融合阶段从 **2.3 s 降到 0.1 ms（-2.3 s）**；端到端中位数从 23.3 s 降到 22.0 s（**-1.3 s，-5.8%**）。差值小于 2.3 s，是因为两次运行不在同一时间，生成、路由的网络波动抵消了一部分收益。
- RRF 去掉的是一次固定成本；生成仍是绝对瓶颈，路由与问题重写合计仍占约三分之一。

## 2. 方法

### 2.1 配置切换

- `fusion.method` 由 `"rerank"` 改为 `"rrf"`，`k = 60`，两路权重 `[1.0, 1.0]`。
- RRF 公式：`score(d) = Σ w_i / (k + rank_i(d))`，只使用两路检索结果的**名次**，不读正文。
- 不再构建和调用远程 `Qwen/Qwen3-Reranker-4B`；`Pipeline` 初始化时会跳过 reranker。
- 召回仍是 BM25 与向量各 20 条，去重后交给 RRF，取前 `context_n = 5` 条送生成。

### 2.2 代码改动

- `src/fastrag/rag_graph.py`
  - `RAGState` 新增 `timings`，用 `Annotated` 合并多个节点上报的耗时，避免并行的 BM25 / 向量节点互相覆盖。
  - 新增 `timed` 装饰器，节点执行完把耗时（毫秒）写入 `state["timings"]`。
  - 交互模式在回答结束后打印各阶段耗时。
- `src/fastrag/bench.py`
  - 固定 3 个问题，每题重复 3 次，先预热一次再统计。
  - 阶段统计中的「融合」同时兼容 `rrf` 的 `fusion` 与 `rerank` 的 `rerank` 计时键，并按配置显示阶段名。
  - 输出每题与全部运行的统计表，并把逐次明细写入 JSON。

### 2.3 阶段划分

| 阶段 | 对应节点 | 说明 |
| --- | --- | --- |
| 路由 | `decide_search` | LLM 判断是否需要检索（含结构化输出解析） |
| 问题重写 | `requery` | LLM 把问题改写成检索查询 |
| 召回 | `retrieve_bm25` + `retrieve_vector` | 两路并行，取较慢的一路作为阶段耗时 |
| 融合 | `fuse` | 当前 `method = "rrf"`，纯本地排名融合，无网络请求 |
| 生成 | `answer` | LLM 依据上下文作答 |

### 2.4 计时口径

- 使用 `time.perf_counter()`，单位毫秒，覆盖节点内全部工作（含网络往返）。
- 端到端耗时单独用 `graph.invoke()` 的墙钟时间测量；各阶段之和与端到端基本一致。
- 召回是并行分支，因此「召回」是 `max(BM25, 向量)`，不能把两路相加。
- 融合阶段由 `timed` 装饰器记录，精度为 0.1 ms；0.010 ms 的结果来自独立跑 1000 次的探针。
- 预热用第一个问题跑一次，排除首次建连、懒加载；`Pipeline` 初始化（加载向量、索引）单独计时，不计入统计。

## 6. 分析

### 6.1 成本结构

按每次运行的各阶段占比取中位数：

| 阶段 | 占端到端比例 |
| --- | ---: |
| 生成 | 63.6% |
| 路由 | 20.2% |
| 问题重写 | 15.5% |
| 召回 | 0.8% |
| 融合 | 0.0% |

- **生成是绝对大头**：约 64%，与回答长度强相关。问题 3 的三次回答只有 169–429 字符，生成只需 5.7–7.2 s，端到端随之降到 12.6–15.5 s。
- **路由与重写合计约 36%**：两次完整 LLM 请求，而路由只输出一个布尔值；这是当前最值得合并的固定成本。
- **融合已经可以忽略**：本地 RRF 0.010 ms/次，对端到端没有可见影响，继续优化它没有意义。
- **召回约 0.8%**：BM25 约 20 ms、向量召回约 150 ms，主要花在远程 `embed_query`；并行后取较慢一路。

### 6.2 波动

- 端到端极差大（12.6–30.8 s），标准差 7.1 s，主要由生成阶段（5.7–23.4 s）和回答长度差异造成。
- 路由在 3.1–5.8 s 之间波动，问题重写在 2.1–5.6 s 之间波动；同为远程 LLM 调用，受网络与服务端排队影响明显。
- 召回稳定在 142–255 ms，基本只随远程 embedding 请求波动。

### 6.3 RRF 的取舍

- RRF 只看两路名次，不理解语义；在候选本身排序不佳时，它无法像交叉编码器那样把正文和问题放在一起判断相关性。
- 本次没有做检索质量或回答正确性评测。抽查问题 3 时，RRF 召回的 5 条里有概览页和 multi-agent 页面，回答虽能自洽，但信息来源偏泛。
- 如果后续对质量不满意，可以保留 RRF 作为默认，再对 top 10 做轻量重排（见 7.3），而不是回到对 35 条全量重排。

## 7. 优化建议

1. **合并路由与问题重写**：一次 LLM 调用同时返回 `need_search` 和改写后的查询，预计省下约 3 s（端到端约 15%），是当前最大的固定成本。
2. **给路由减负**：用更小的模型、更短的提示词，或用关键词规则先短路明显不需要检索的问题。
3. **生成侧优化**：保留流式输出改善体感；限制 `max_tokens`、精简 5 条上下文，避免回答过长。
4. **需要 rerank 质量时做两级排序**：先 RRF 粗排取 top 10，再送交叉编码器，按实测可把重排请求压到约 0.24 s（复用连接），而不是 2.3 s。
5. **缓存 BM25 索引**：现在每次查询都从磁盘重新加载（约 20 ms），收益小但改动简单。

## 8. 复现与局限

### 复现

```bash
# 前置：.env 里配置 SILICONFLOW_API_KEY，且本地已有向量与 BM25 索引
uv run python -m fastrag.embed_chunks      # 生成 data/embeddings/
uv run python -m fastrag.keyword_search build
# 若环境变量里有 socks 代理，httpx 会拒绝初始化 ChatOpenAI，需要先去掉
env -u ALL_PROXY -u all_proxy uv run python -m fastrag.bench
```

明细默认写入 `data/bench/results.json`，可用 `--runs` 调整重复次数、`--json` 指定输出路径。把 `config/rag.toml` 的 `fusion.method` 改回 `"rerank"` 即可复现附录 A。

### 局限

- 每题只有 3 次样本，标准差很大，结论更适合看中位数和量级，不宜当作精确基准。
- 所有耗时都包含公网 API 往返，绝对数值会随网络、服务负载和时间变化。
- RRF 与 rerank 是两次独立运行，中间模型接口的波动无法消除；严格对比需要交替运行并增加样本。
- 只测了 3 个问题，且都触发检索，`need_search = false` 的短路路径没有样本。
- 只测耗时，没有评估检索质量、回答正确性和幻觉率。
- 基准使用非流式 `graph.invoke()`，生成时间按完整回答计入；交互模式的流式输出首 token 延迟未单独测量。

## 附录 B：重排阶段为什么是 2 秒级

> 2026-10-26 追加。切换前的配置是 `fusion.method = "rerank"`，本节解释当时「重排」为什么是 2 秒级，而本地 RRF 只要 0.010 ms。当前配置已切换为 RRF，结果见正文。

### B.1 两个不同的方案

| 方案 | 实际执行内容 | 实测 |
| --- | --- | --- |
| `fusion.method = "rerank"`（切换前） | 调用 SiliconFlow 的 `Qwen/Qwen3-Reranker-4B`，把 query 与每条候选拼成一对送进 4B 交叉编码器打分 | 1.5–5.5 s |
| `fusion.method = "rrf"`（当前） | 纯本地排名融合：`score(d) = Σ w / (k + rank)`，只做字典累加和排序 | 0.010 ms |

`src/fastrag/rag_graph.py` 的 `fuse` 节点按配置二选一：`rerank` 时调用 `rerank_chunks`，`rrf` 时调用 `rrf_fuse`。基准里的阶段名「重排」来自 `method = "rerank"`；切到 `rrf` 后同一节点记作「融合」。

所以“RRF 应该在 ms 级别”这个判断是对的，只是切换前流水线并没有走 RRF。

### B.2 2 秒花在哪里

以问题“LangGraph 中如何实现 human-in-the-loop？”为例，对 `fuse` 内部逐段测量：

- BM25 与向量各召回 20 条，按 `id` 去重后 **35 条**；
- 35 条文本共 **16,746 token**（单条中位数 497），请求体约 **72 KB**；
- `rerank` 的 `top_n = 5` 只限制返回条数，不减少打分工作量，35 条都要过模型。

| 环节 | 实测 | 条件 |
| --- | ---: | --- |
| 本地 `_merge` 去重（20+20 → 35） | 0.003 ms | 1000 次平均 |
| 本地 `rrf_fuse`（35 条） | 0.010 ms | 1000 次平均 |
| `/rerank` 1 条 / 449 token | 95 ms | 复用连接，3 次中位数 |
| `/rerank` 5 条 / 2,450 token | 241 ms | 同上 |
| `/rerank` 10 条 / 4,918 token | 240 ms | 同上 |
| `/rerank` 20 条 / 9,880 token | 392 ms | 同上 |
| `/rerank` 35 条 / 16,746 token | 916 ms | 同上；另一次实验 574–708 ms |
| `/rerank` 35 条（每次新建连接） | 中位数 1,962 ms（628–7,978） | 与复用连接交替测 4 次 |
| 库内 `rerank_chunks`（每次新建连接） | 924–2,368 ms | 3 次 |

即使完全复用连接，35 条候选也要约 0.6–1.3 s（两次实验的中位数分别为 0.61 s 和 0.92 s）；新建连接时中位数约 2 s，和基准里“重排中位数 2.3 s”是同一量级。耗时随候选数/token 数增长明显：1 条约 0.1 s，35 条约 0.6–1.3 s。

### B.3 四个原因（按影响排序）

1. **方案选型是主因：这是远程 rerank，不是 RRF。**
   RRF 只读两条排名列表里的 `id`，不读正文，也不调用任何模型；交叉编码器必须把 query 和每条候选正文一起过一遍 4B 模型，天然是几十毫秒到近一秒（随候选数增长）。

2. **输入比配置注释看起来更大：35 条、1.67 万 token。**
   `config/rag.toml` 写的是“两路各 20 条”，但两路合并去重后仍有 35 条，且全部送重排。`config/reranker.toml` 里的 `candidates = 20` 只用于 `fastrag.reranker` 的演示脚本，不参与 RAG 图。

3. **`langchain-reranker` 每次请求都新建 HTTP 连接。**
   `langchain_reranker/rerankers/http_reranker.py` 的 `HttpReranker.rerank()` 直接用模块级 `httpx.post(...)`，没有复用 `httpx.Client` 的连接池。因此每次重排都要重新做 TCP/TLS 握手（本机走 HTTP 代理，还会多一次 CONNECT）。同一批 35 条、与复用连接交替测量：新建连接中位数 1,962 ms，复用连接中位数 612 ms，前者抖动也大得多（628–7,978 ms）。

4. **公网加代理放大抖动。**
   rerank 基准里重排阶段的 9 次样本为 1.5–5.5 s，标准差 1.27 s。服务端排队、代理链路和连接新建叠加，使单次耗时可能突然到 5 s 以上；这部分不是算法本身的开销。

补充：本机 curl 到 API 的 TLS 握手约 44–53 ms，所以“新建连接比复用连接多出 1.3 s”不能全记在 TLS 上，多出来的部分在代理隧道和服务端的连接建立/调度上。但“库内每次新建连接”这个事实是明确的，也是可优化的。

### B.4 为什么 RRF 只要 0.010 ms

`rrf.py` 的实现只做两件事：遍历两路候选（最多 40 条）累加 `weight / (k + rank)`，再对 35 个 `id` 排一次序。复杂度是 O(候选数 × 路数 + n log n)，没有任何 I/O 和模型推理，所以实测每次约 10 微秒——比一次网络往返（约 60 ms）小三个数量级以上。

它换来的是“快”，代价是不理解语义：RRF 只信两路检索器给出的名次，无法像交叉编码器那样判断正文与问题的真实相关性。

### B.5 如果既要速度又要 rerank 质量

1. **改用 RRF**（当前做法）：融合阶段从约 2.3 s 降到约 0.01 ms，端到端按阶段口径减少约 2.3 s；需要重新评估回答质量。
2. **先 RRF 粗排，再 rerank 精排**：RRF 从 35 条里取 top 10 送交叉编码器，按实测可把重排请求压到约 0.24 s（复用连接时），兼顾延迟和质量。
3. **复用 HTTP 连接**：自定义一个基于 `httpx.Client` 的 reranker（或给 `langchain-reranker` 提 issue/PR），省掉每次的握手与代理隧道；交替测量中位数约从 2.0 s 降到 0.6–0.9 s。
4. **减少候选或本地部署**：下调两路 `candidates`，或把重排模型放到内网/本机，消除公网抖动。

### B.6 本节测量说明

- 只取了一个问题、一个改写后的查询，每组 3–4 次，数值用于判断量级和归因，不代表稳定基准。
- 机器经本地 HTTP 代理访问 SiliconFlow；不走代理时绝对耗时可能不同，但“远程 rerank 远慢于本地 RRF”的结论不变。
- “新建/复用连接”的对比在同一次实验中交替执行，避免服务负载随时间漂移完全掩盖差异；两种方式仍各有 0.6–8 s 的抖动。
