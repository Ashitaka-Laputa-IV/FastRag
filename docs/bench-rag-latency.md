# RAG 各阶段耗时基准报告

- 日期：2026-10-26
- 分支：`bench`（基于 `upstream/dev`，基线 `12edf0d`）
- 脚本：`src/fastrag/bench.py`
- 原始明细：`data/bench/results.json`（`data/` 已被忽略，不随仓库提交）
- 测量方式：3 个问题 × 每题 3 次，另加 1 次预热（不计入统计）

## 1. 摘要

- 9 次运行的端到端耗时中位数为 **23.3 s**，范围 19.1–39.5 s。
- 主要成本在远程模型调用：**生成约 60%**，路由约 16%，问题重写约 14%，重排约 8%。
- 本地召回（BM25 + 向量）中位数只有 **147 ms**，占端到端 **0.6%**，不是瓶颈。
- 路由、重写、重排、生成都是网络请求，单次波动可达数倍；一次路由请求出现了 23.6 s 的离群值。
- 生成耗时与回答长度明显相关（9 个样本的 Pearson r ≈ 0.72，约 94 字符/秒）。

## 2. 方法

### 2.1 代码改动

- `src/fastrag/rag_graph.py`
  - `RAGState` 新增 `timings`，用 `Annotated` 合并多个节点上报的耗时，避免并行的 BM25 / 向量节点互相覆盖。
  - 新增 `timed` 装饰器，节点执行完把耗时（毫秒）写入 `state["timings"]`。
  - 交互模式在回答结束后打印各阶段耗时。
- `src/fastrag/bench.py`
  - 固定 3 个问题，每题重复 3 次，先预热一次再统计。
  - 输出每题与全部运行的统计表，并把逐次明细写入 JSON。

### 2.2 阶段划分

| 阶段 | 对应节点 | 说明 |
| --- | --- | --- |
| 路由 | `decide_search` | LLM 判断是否需要检索（含结构化输出解析） |
| 问题重写 | `requery` | LLM 把问题改写成检索查询 |
| 召回 | `retrieve_bm25` + `retrieve_vector` | 两路并行，取较慢的一路作为阶段耗时 |
| 重排 | `fuse` | 当前配置 `method = "rerank"`，耗时约等于重排请求；若改为 `rrf` 则记作「融合」 |
| 生成 | `answer` | LLM 依据上下文作答 |

### 2.3 计时口径

- 使用 `time.perf_counter()`，单位毫秒，覆盖节点内全部工作（含网络往返）。
- 端到端耗时单独用 `graph.invoke()` 的墙钟时间测量；各阶段之和与端到端基本一致。
- 召回是并行分支，因此阶段表里的「召回」是 `max(BM25, 向量)`，不能把两路相加。
- 预热用第一个问题跑一次，排除首次建连、懒加载；`Pipeline` 初始化（加载向量、索引、重排器）单独计时，不计入统计。

## 5. 分析

### 5.1 成本结构

按每次运行的各阶段占比取中位数（各阶段之和与端到端之比为 100%，图编排本身的开销可忽略）：

| 阶段 | 占端到端比例 |
| --- | ---: |
| 生成 | 59.8% |
| 路由 | 15.6% |
| 问题重写 | 14.2% |
| 重排 | 8.4% |
| 召回 | 0.6% |

- **生成是绝对大头**：约 60%，且与回答长度正相关，属于“按 token 付费”的耗时。
- **路由与重写合计约 30%**：两者各是一次完整的 LLM 请求，而路由只输出一个布尔值，性价比很低。
- **重排约 8%**：一次 `/rerank` 请求，中位数约 2.3 s，20 条候选。
- **召回几乎免费**：BM25 约 20 ms，向量召回约 150 ms（主要是一次远程 `embed_query`），并行后取较慢一路。

### 5.2 波动

- 同题同配置的端到端耗时相差可达 1.7 倍（问题 2：22.5–39.5 s），主要来自远程接口排队与网络抖动。
- 问题 2 第 1 次的路由耗时 23.6 s，是明显离群值，把该阶段平均值从约 3.3 s 拉到 10.2 s；因此报告同时给出中位数。
- 生成阶段的标准差最大（5.0 s），既有接口波动，也因为回答长度在 868–2315 字符之间变化。

### 5.3 其他观察

- 生成速度约 94 字符/秒，与回答长度的相关系数 r ≈ 0.72；控制输出长度比优化检索更直接地降低端到端时间。
- BM25 每次查询都会从磁盘重新加载索引（约 20 ms），虽然占比极小，但缓存后可以降到毫秒级。
- 本地向量计算与排序可忽略，说明当前瓶颈完全在远程服务，不在检索算法本身。

## 6. 优化建议

1. **合并路由与问题重写**：一次 LLM 调用同时返回 `need_search` 和改写后的查询，预计省下约 3 s（端到端约 14%）。
2. **给路由减负**：用更小的模型、更短的提示词，或用关键词规则先短路明显不需要检索的问题。
3. **生成侧优化**：流式输出改善体感；同时限制 `max_tokens`、精简上下文（当前 5 条片段），避免回答过长。
4. **下调重排候选**：20 条降到 10 条可近似减半重排耗时，需要配套评估召回质量。
5. **缓存 BM25 索引**：`Pipeline` 初始化时就加载，避免每次查询重复读盘（收益小，但改动简单）。

## 7. 复现与局限

### 复现

```bash
# 前置：.env 里配置 SILICONFLOW_API_KEY，且本地已有向量与 BM25 索引
uv run python -m fastrag.embed_chunks      # 生成 data/embeddings/
uv run python -m fastrag.keyword_search build
# 若环境变量里有 socks 代理，httpx 会拒绝初始化 ChatOpenAI，需要先去掉
env -u ALL_PROXY -u all_proxy uv run python -m fastrag.bench
```

明细默认写入 `data/bench/results.json`，可用 `--runs` 调整重复次数、`--json` 指定输出路径。

### 局限

- 每题只有 3 次样本，标准差很大，结论更适合看中位数和量级，不宜当作精确基准。
- 所有耗时都包含公网 API 往返，绝对数值会随网络、服务负载和时间变化。
- 只测了 `fusion.method = "rerank"`、候选 20 的配置，未覆盖 RRF、不同 `candidates` / `context_n`。
- 三个问题都需要检索，`need_search = false` 的短路路径没有样本。
- 基准使用非流式 `graph.invoke()`，生成时间按完整回答计入；交互模式的流式输出首 token 延迟未单独测量。
