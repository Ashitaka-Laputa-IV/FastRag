- 合并后跑了两次完整的 9 次基准（`09:06Z` 与 `09:28Z`），端到端中位数分别为 **23.7 s** 和 **22.3 s**，与合并前的 **22.0 s** 在同一波动区间内；两次合并后样本合计 18 次的中位数为 **23.3 s**。

## 6. 分析

### 6.1 合并两次 LLM 调用没有换来速度

- 旧报告的建议是「合并路由与问题重写，预计省下约 3 s」。实测没有发生：合并前逐次 `route + requery` 中位数 7166 ms，合并后 18 次 `plan_search` 中位数 7059 ms，差距 1.5%，在 4431–11311 ms 的波动范围内。
- 原因在输出侧：`prompts/search_plan.txt` 要求一次返回 `need_search`、`bm25_query`、`vector_query` 三个字段，其中两条查询都是完整英文表述（向量查询还是自然语言问句）；旧流程的 `decide_search` 只输出一个布尔值、`requery` 只输出一条查询。少一次往返省下的时间，被多出来的输出 token 和结构化输出解析吃掉了。
- 因此「减少 LLM 调用次数」本身不是优化点；要真正降这一段的耗时，得减少输出（例如先判是否需要检索，再按需生成单条查询），或换更快的模型。

### 6.2 生成仍是绝对瓶颈

- 按每次运行取占比中位数：生成 **65.1%**、检索规划 **33.8%**、召回 0.7%、融合 0.0%（合并前分别是 63.6% / 35.6% / 0.8% / 0.0%）。
- 生成耗时与回答长度强相关：复测里 Q2 三次回答 789–1459 字符，生成 10.8–14.1 s；Q3 三次 951–1295 字符，生成 16.2–22.8 s。同一个问题在不同次运行间也能差一倍以上，说明服务端排队/网络的影响不小于回答长度。
- 召回稳定在 0.15–0.33 s（跳过检索的那次除外），融合稳定 0.1 ms，都不值得再优化。

### 6.3 `need_search` 判定出现回归

- 合并前 9 次全部判定需要检索；合并后 18 次里有 1 次（Q1 的第 1 次）判定不需要，直接作答 59 字符，端到端 9.7 s。
- 该问题明确指向 LangGraph 文档概念，正确行为应当是检索。合并后的提示词把「判断」和「写两条查询」放在同一个结构化输出里，判定部分只占很小篇幅，可能是误判来源之一；另一可能是 `temperature = 0.7` 带来的随机性。
- 这既影响答案质量，也污染统计：它把 Q1 的最小值拉到 9.7 s、把「全部 9 次」的召回最小值记成 0.0 ms。本文保留原始样本，没有剔除，只在解读时单独标注。
- 建议：单独开 issue，考虑把 `plan_search` 的 `need_search` 判定与查询生成拆开、降低判定温度，或在基准脚本里对 `need_search = false` 单独计数并在汇总时提示。

### 6.4 其余配置改动影响很小

- BM25 零分过滤（`bm25.min_score = 0.0`）与权重 `[1.1, 1.0]` 只影响排序，不产生额外的网络请求；召回中位数从 180 ms 降到 160 ms，属于 embedding 请求波动，不能归因于这次改动。
- 召回仍是 BM25 约 20–26 ms、向量约 150–330 ms，主要花在远程 `embed_query`；两路并行后取较慢一路。
- 融合仍是本地 RRF，0.1 ms，与合并前一致。

## 7. 局限

- 每题只有 3 次样本，两次复测合计 18 次；标准差普遍在 1–14 s，结论只看中位数与量级。
- 旧基准走本地代理、复测直连，网络路径不同；生成阶段正好是波动最大的阶段，端到端差异不可完全归因于代码或配置。
- 合并前后阶段名不同（`route` + `requery` → `plan`），只能按「两次调用之和」对照，无法逐阶段严格比较。
- 只测耗时，没有评估检索质量、回答正确性与幻觉率；`need_search = false` 的那次属于质量问题，本文只做记录。
- 3 个问题都会（正常时）触发检索，没有覆盖「确实不需要检索」的正常短路样本。
- 基准使用非流式 `graph.invoke()`，流式首 token 延迟未测量。
