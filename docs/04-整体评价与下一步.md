# 04 · 整体评价与下一步

> 代码基线：`dev@2d9604f`，版本 `0.2.0`。
>
> 评价范围：`src/fastrag/` 全部源码、默认配置、提示词与 CLI 行为。
>
> 方法：静态通读 + 调用链核对 + 对照仓库另一分支 `docs/review-duplication` 的三份审阅材料（重复率、第三方替代、最小化方案）。本文不重复那些材料的所有数据，只保留对当前决策有用的结论。

## 1. 一句话结论

**这是一个边界清楚、工程习惯不错的小型 RAG 实现；它已经过了「能不能跑」的阶段，下一步的关键不是换框架，而是「能不能证明它一直跑对」。**

具体说：

- 架构方向不需要推翻；
- 数据产物与降级设计是亮点；
- 最大的短板是**没有测试、没有评测、没有 CI**；
- 其次是几处「同一职责两套实现」和「静默失败」；
- 不建议用 Haystack/LlamaIndex/agent/向量数据库重写。

## 2. 评分表

评分只针对「当前定位」：一个单机、单用户、几千到几万 chunk 的 RAG 库/CLI。拿生产级多租户服务的标准打分会不公平。

| 维度 | 评分 | 理由 |
| --- | ---: | --- |
| 架构与依赖方向 | 5 / 5 | 分层清楚，单向依赖，领域类型稳定 |
| 数据完整性 | 4 / 5 | 内容寻址、指纹校验、唯一真源；单文件原子写，但 BM25 目录与 npy+manifest 不是整体事务 |
| 检索设计 | 4 / 5 | 双路 + RRF/rerank 合理；缺多样性/阈值/评测 |
| 生成与容错 | 3.5 / 5 | 路由/重排/回答都有降级；但捕获过宽、无引用核验 |
| 可运维性 | 2.5 / 5 | 有日志与 metadata；缺指标、追踪、锁、服务化 |
| 可验证性 | 1.5 / 5 | 无测试、无 CI、无评测集 |
| 文档与可读性 | 4 / 5 | 中文文档/注释完整；缺少面向学习者的系统材料（本套文档是补充） |
| **作为教学项目** | **4.5 / 5** | 结构完整、体量适中、取舍可讲 |
| **作为生产 RAG** | **2.5 / 5** | 缺测试、评测、观测、并发与规模化能力 |

一句话：**作为「读懂 RAG 并二次开发」的骨架，它很好；作为「明天上线」的服务，它还差几道工程闸门。**

## 3. 做得好的地方

### 3.1 分层与依赖方向

`cli → pipeline → index/retrieve/llm → ingest/config → domain/errors` 这条线在代码里基本没有被破坏：

- CLI 命令只解析参数、调用下层、打印；
- `pipeline` 负责装配与降级，不直接读文件；
- `index` 只关心 chunk、向量、BM25；
- `domain` 不依赖 LangChain；
- `config` 不依赖 pipeline。

这让每一层都可以单独理解、单独替换。对比很多「一个 `main.py` 里塞完 RAG」的项目，这是明显的工程优势。

### 3.2 领域类型与通道模型

`Chunk` / `ScoredChunk` 不是装饰性的 dataclass，它们在保护边界：

- `Chunk` 强制携带 `source/start/end/token_count`，让「来源可追溯」成为类型的一部分；
- `ScoredChunk` 强制携带 `channel/rank`，让融合层不需要猜「这条结果来自哪里」；
- `Document` 只出现在 `retrieve/rerank.py` 的内部适配里，没有污染 `domain` 与 `pipeline`。

这是一个很成熟的选择。很多项目一开始图省事，让 LangChain `Document` 贯穿全链路，最后发现 metadata 变成无类型的垃圾袋。

### 3.3 数据产物的完整性设计

这是项目最值得保留的部分：

- `chunks.jsonl` 是唯一真源；
- chunk id 内容寻址；
- 向量 manifest 记录模型/维度/ids；
- BM25 meta 严格校验 digest 与参数；
- `chunks.jsonl`、向量文件、manifest/meta 和单文件下载使用临时文件 + 原子替换；BM25 索引目录由 `bm25s.save` 直接写入，不保证整体原子性；
- `prepare` 把切块、嵌入、索引串成一条可重复的流水线。

它解决的不是「怎么检索」，而是「怎么保证检索用的数据没有悄悄错位」。后一个问题通常更贵：线上答案变差时，你很难发现是索引对不上，还是模型变笨了。

### 3.4 失败就地降级

三个关键降级点设计得很务实：

| 失败点 | 降级 | 产品含义 |
| --- | --- | --- |
| 路由模型 | 用原问题检索两路 | 宁可多检，不放弃资料 |
| 重排服务 | 退回 RRF | 排序差一点，但结果仍可用 |
| 回答模型 | 空回答 + fallback | 单轮失败不拖垮交互 |

降级发生在「离失败点最近」的地方，而不是在最外层统一 try。这让每个降级都有明确的语义。

### 3.5 配置严格且集中

- 单份 TOML，没有多份配置漂移；
- pydantic `extra="forbid"`，拼错键立即报错；
- endpoint 引用、fallback 链、权重、切块参数都有交叉校验；
- `.env` 与配置加载分离，`load_config()` 不产生读 `.env` 的隐式副作用；
- 本地/云端只是两份配置，不是两套代码。

### 3.6 懒加载与打包资源

`ResourceBundle` 的 `cached_property` 让：

- `import fastrag` 无 I/O；
- `RagPipeline.__init__` 无 I/O；`RagPipeline.from_config()` 会读 TOML，但不读 `.env`；
- 寒暄类问题不需要加载索引；
- 测试可以注入替身；
- 同一个 pipeline 复用资源。

包内配置与提示词通过 `importlib.resources` 读取，wheel 安装后仍然可用；用户又可以用 `$FASTRAG_HOME` 覆盖。这是一个兼顾「开箱即用」与「可定制」的设计。

### 3.7 中文文档与提示词

README、docstring、CLI 输出、提示词都是中文，且没有把项目限定为「LangChain 文档助手」——`chat.txt` 明确可以回答通用问题。对中文用户和二次开发者友好。

## 4. 主要问题

按「先影响正确性，再影响可维护性，最后影响规模」排序。

### 4.1 P0：没有验证网

**证据：**

- 没有 `tests/`；
- 没有 CI；
- 没有 linter/formatter 配置；
- `AGENTS.md` 明确写「没有 test suite，验证用 CLI」。

**影响：**

- 任何重构都只能靠手跑命令；
- 数据产物、降级路径、配置校验这些「最容易静默坏」的地方没有回归保护；
- 本篇建议的收敛（原子写、提示词、检索编排）没有安全网，风险会被放大。

**这是当前第一优先级，高于任何功能改进。**

### 4.2 P0：提示词渲染会静默放过拼写错误

`llm/prompts.py` 与 `pipeline/nodes.py` 都用：

```python
Template(prompt).safe_substitute(values)
```

如果提示词里写错占位符，例如 `$questoin`，`safe_substitute` 不会报错，而是把字面量 `$questoin` 发给模型。模型可能仍然能回答，但你会得到难以定位的质量问题。

同时存在两套渲染实现：

- `llm.prompts.render`
- `pipeline.nodes._render`

以及两套提示词名单：

- `llm.prompts.REQUIRED`（未使用）
- `pipeline.resources.PROMPT_NAMES`

**建议：**

1. 先改成 `Template(...).substitute(values)`，让缺变量立即 `KeyError`；
2. 只保留一个 `render` 函数，`nodes` 复用它；
3. 只保留一个 `PROMPT_NAMES`，删除 `REQUIRED`；
4. 如果未来要 system/human 角色，再迁移到 `ChatPromptTemplate`。

### 4.3 P0：流式依赖实验性 API，并主动压掉警告

`pipeline/runner.py`：

```python
warnings.filterwarnings("ignore", message="Pydantic serializer warnings")
warnings.filterwarnings(
    "ignore",
    message="The v3 streaming protocol on Pregel is experimental.",
)
run = self.graph.stream_events({"question": question}, version="v3")
```

这不是错误，但意味着：

- LangGraph 升级可能改变 `stream_events` 的行为；
- 警告被压掉，升级后的不兼容不会在日志里显现；
- `stream()` 的 token 只来自 `answer` 节点，其他节点没有流式事件。

**建议：**

- 给 `langgraph` 加上限（例如 `<2`），并在 CI 里跑一个最小流式冒烟测试；
- 或者评估改用稳定的 `astream_events` / 自定义回调；
- 至少不要全局压掉所有 Pydantic serializer 警告，缩小匹配范围。

### 4.4 P0：依赖没有上限

`pyproject.toml` 里多数依赖是 `>=`，没有上限。这个项目深度依赖：

- `langchain-core` 的 `Document` / `Embeddings` / `Runnable`；
- `langgraph` 的 v3 流式协议；
- `langchain-core` 的 `BaseDocumentCompressor` / `Document`，以及 `langchain-reranker` 的 `init_reranker`；
- `bm25s` 的索引文件格式。

任何一个大版本升级都可能破坏行为。**建议给核心依赖加兼容上限，并在 CI 里固定一组已知可用版本。**

### 4.5 P1：同一职责多处实现

字面克隆率不高，但语义重复存在：

| 职责 | 位置 | 建议 |
| --- | --- | --- |
| 原子写 | `ingest/artifacts.py` 的 json/npy、`chunker.write_chunks`、`download.download` | 抽一个 `atomic_write()` 上下文管理器 |
| 提示词渲染 | `llm.prompts.render`、`pipeline.nodes._render` | 只留一处 |
| 提示词名单 | `prompts.REQUIRED`、`resources.PROMPT_NAMES` | 只留一处，删死代码 |
| 检索编排 | `nodes.retrieve_* / fuse`、`cli/commands/rrf.py` | 抽 `retrieve_all()` 或 `HybridRetriever` |
| fallback 链遍历 | `config/models.py` 的 route/answer 两段 while | 抽 `_iter_roles()` |
| manifest 参数 | `dense._manifest_key` / `_load_previous` | 参数 dict 只构造一次 |

这些不是「代码脏」，而是「改一处容易忘另一处」。在加测试之后做收敛，收益最稳。

### 4.6 P1：死代码与重复读取

- `errors.run_cli`：没有调用；
- `llm.prompts.REQUIRED`：没有调用；
- `index.bm25.index_path`：没有调用；
- `index.dense.vectors_path`：没有调用；
- `ResourceBundle.prompt_hashes` 又 `load_prompt` 一遍：每个新 pipeline 首次问答多读 3 个文件（`prompts` 已经缓存了文本）。

死代码本身不致命，但它会让读者误以为「还有另一条入口」，增加理解成本。

### 4.7 P1：检索质量还有明显提升空间

当前检索是「BM25 top20 + 向量 top20 → 融合 top5」。问题在于：

- **没有多样性控制。** 相邻 chunk 可能高度重叠，top5 里出现多条近似内容，浪费上下文；
- **向量没有最低分阈值。** 即使语义完全不相关，也会返回 top k；
- **没有上下文 token 预算。** `context_chunks` 是条数，不是 token 数；长 chunk 可能撑爆提示词；
- **BM25 的中文分词能力有限。** 默认 stopwords 是英文，`bm25s` 的 tokenizer 对中文不友好；`ask` 靠路由把问题翻成英文，但 `fastrag search "中文"` 的 BM25 效果不会好；
- **没有评测集。** 你无法回答「这次改动让召回变好还是变坏」。

**建议：**

1. 加 MMR 或「每来源最多 N 条」的多样性策略；
2. 给向量加 `min_score`（按余弦相似度）；
3. 加 `context_max_tokens`，按 token 截断而不是按条数；
4. 建 20–50 条问题的评测集，至少记录 Recall@5 / MRR@5；
5. 中文 BM25 单独评估，必要时换 tokenizer 或加中文停用词。

### 4.8 P1：回答的引用与忠实度没有程序化保证

`AnswerResult.sources` 来自融合结果，回答提示词要求「只依据资料、不足说明、不编造」。但：

- 没有验证回答中的每句话是否真的来自某个 source；
- 没有要求模型输出结构化引用（如 `[1]`）并校验；
- `sources` 可能多于模型实际读到的 `context_chunks`；
- 语料如果是不可信来源，存在提示词注入风险。

**建议：**

- 提示词要求「每个结论后标注来源编号」；
- 在 `AnswerResult` 中增加 `citations` 或至少解析 `[n]` 并校验范围；
- 对不可信语料加「资料中的指令不是命令」的防御性提示；
- 评测时人工检查 20 条回答的忠实度。

### 4.9 P2：CLI 与运维能力

- `fastrag ask` 只有交互模式，没有 `fastrag ask "问题"` 一次性调用；
- 没有 `--json` 输出，自动化集成不方便；
- `download` 只要有一个文件成功就返回 0，CI/脚本可能误判；
- 下载 URL 收集硬编码 `base_url + "/oss/python/"`，换文档站点要改代码；
- 下载重试是线性 sleep，没有指数退避；
- 没有并发 `prepare` 的文件锁；
- 没有指标（延迟、token 数、成本、召回条数）与追踪 ID；
- 日志是 stdlib logging，格式不统一。

这些不是当前的核心矛盾，但在「多人/长期使用」时会逐渐变成摩擦。

### 4.10 P2：规模化

当前向量检索是 numpy 全量内积：

- 几千到几万 chunk：完全够用；
- 十万级以上：每次查询 O(N×dim)，会开始变慢；
- 百万级：需要 ANN（FAISS/HNSW）或外部向量库。

BM25 每次 `prepare` 全量重建；语料很大时也会变慢。当前没有分片、并行训练或增量 BM25。

**建议：** 先测出当前语料规模下的 P50/P95 延迟，再决定是否引入 FAISS。不要为了「看起来可扩展」提前上向量数据库。

## 5. 风险矩阵

| 风险 | 可能性 | 影响 | 当前缓解 | 建议 |
| --- | --- | --- | --- | --- |
| 语料/索引错位 | 中 | 高 | digest + ids + meta 校验 | 加测试覆盖「改语料后必须重建」 |
| 提示词拼写错误 | 中 | 中 | 无（`safe_substitute`） | 改严格渲染 + 测试 |
| API 服务故障 | 中 | 中 | 路由/重排/回答降级 | 加熔断/超时/指标 |
| 回答幻觉 | 高 | 中 | 提示词约束 + sources | 引用校验 + 评测 |
| 提示词注入 | 低（可信语料）/高（外部语料） | 高 | 无 | 指令隔离 + 来源白名单 |
| 依赖大版本破坏 | 中 | 高 | 无上限 | 加上限 + CI 固定版本 |
| 并发 `prepare` 写坏 | 低 | 高 | 单文件原子写（BM25 目录除外） | 加文件锁 |
| 部分下载失败被忽略 | 中 | 低 | 打印失败列表 | 明确退出码策略 |
| 流式 API 变更 | 中 | 中 | 压掉警告 | 固定版本 + 冒烟测试 |

## 6. 不建议做的事

这一节和「建议做什么」同样重要。

| 不建议 | 原因 |
| --- | --- |
| 用 Haystack / LlamaIndex / txtai 重写 | 会替换整个项目的控制权，依赖与概念成倍增加，当前规模不需要 |
| 把固定 DAG 换成 agent | 流程本来是确定的四步；agent 会增加不确定性、延迟与调试难度 |
| 引入 Chroma / Qdrant / Milvus | 几千到几万 chunk 用 numpy 足够；外部服务带来部署、备份、网络与权限问题 |
| 用 `EnsembleRetriever` / `langchain-classic` | v1 已把 legacy 拆走；为 25 行 RRF 引入整个 legacy 包不划算 |
| 用 `InMemoryVectorStore.dump/load` 替代 npy | dump 是 JSON，矩阵会膨胀；npy 更适合数值数据 |
| 强制 `Document` 贯穿全项目 | 会破坏 `ScoredChunk` 的清晰边界，收益只是少一个 dataclass |
| 为了「少代码」砍掉所有调试命令 | `search/rrf/rerank` 是定位检索问题的关键工具；可以合并，不要盲删 |
| 在没有测试前做大规模重构 | 无法证明行为不变；先补验证网 |

## 7. 下一步路线图

下面按「先建立证据，再改代码，再提质量，最后扩规模」排序。

### Phase 0：建立验证网（1–2 天）

**目标：让任何改动都能被快速验证。**

- 加 `pytest` 与 `ruff`（dev 依赖）；
- 加最小测试集：
  1. `chunker`：`text == original[start:end]`，模板头偏移正确；
  2. `rrf_fuse`：已知排名与权重下的分数/顺序；空输入；重复 id；
  3. `config`：最小 TOML 可加载；拼错键/缺字段/非法权重会报错；
  4. `artifacts`：manifest 不匹配时 `matches` 为 false；单文件原子写失败不留目标文件（BM25 目录不在此保证内）；
  5. `prompts`：缺变量必须报错（改严格渲染后）；
  6. `graph`：用 fake resources 验证 `need_search=False` 走 `answer`，`True` 走两路，路由异常走降级；
- 加 GitHub Actions：`ruff check` + `pytest`；
- 建 20–30 条问题的评测集，记录当前 `search` / `rrf` / `ask` 输出作为基线；
- 打 tag：`v0.2.0-baseline`。

**验收：** 本地与 CI 全绿；评测基线可重复。

### Phase 1：收敛重复与静默失败（1–2 天）

**目标：同样的职责只有一处实现。**

- `atomic_write()` 统一 4 处单文件原子写；
- `render()` 统一 2 处提示词渲染，改 `substitute`；
- `PROMPT_NAMES` 单一来源，删 `REQUIRED`；
- 抽 `retrieve_all()` / `HybridRetriever`，让 `nodes` 与 `rrf` 共用；
- 抽 fallback 链遍历；
- 删 `run_cli`、`index_path`、`vectors_path`；
- 给核心依赖加上限；
- 减少宽泛的 `except Exception`，至少保留类型与日志上下文。

**验收：** 代码量下降约 100 行；测试全绿；提示词拼写错误能在测试中暴露。

### Phase 2：检索与回答质量（3–5 天）

**目标：让「答得更好」可测量。**

- 加 MMR 或每来源多样性限制；
- 加向量 `min_score`；
- 加 `context_max_tokens`，按 token 预算截断；
- 回答提示词要求引用编号，并解析/校验 `[n]`；
- 改进 `search_plan` 提示词：明确「寒暄/常识不检索」「代码/API 用关键词」「自然语言问句用向量」；
- 用评测集对比改动前后的 Recall@5、MRR@5、人工忠实度；
- 对中文 BM25 做一次专项评估。

**验收：** 召回指标不退化；上下文重复率下降；20 条人工检查的忠实度可接受。

### Phase 3：运维与规模（按需，1 周左右）

**目标：从「本机可用」到「可持续运行」。**

- 结构化日志：`trace_id`、耗时、通道条数、模型、token 数；
- 指标：QPS、P50/P95、嵌入批耗时、重排耗时、fallback 次数；
- 给 `prepare` 加文件锁；
- 嵌入批处理并发化/异步化；
- 评估 FAISS/HNSW（语料 > 10 万时）；
- 评估 BM25 增量或分片重建；
- 加 `ask "问题" --json` 一次性接口，方便脚本集成；
- 评估 HTTP 服务封装（FastAPI 等）。

**验收：** 故障注入下可定位；并发 `prepare` 不互相破坏；延迟有基线。

### Phase 4：产品化（可选）

只有明确需要时再做：

- 多轮对话与历史压缩；
- 元数据过滤（按来源/版本/权限）；
- PDF/HTML/Word 解析；
- Web UI / API 鉴权；
- 多租户与配额；
- 引用高亮与原文定位。

这些会显著增加代码量与运维面，不建议在 Phase 0–2 之前做。

## 10. 建议记录的架构决策

把这些写成 ADR（一页一个），以后争论时不用重新翻代码：

1. **ADR-001：固定 DAG，不用 agent。** 当前任务是确定的四步，可预测性优先。
2. **ADR-002：chunks.jsonl 是唯一真源，派生产物可重建。** 内容寻址 + 指纹校验。
3. **ADR-003：当前规模不引入向量数据库。** numpy 全量内积足够；十万级以上再评估 FAISS。
4. **ADR-004：失败就地降级，检索异常不静默。** 路由/重排/回答可降级，数据错误必须暴露。
5. **ADR-005：单份 TOML + 严格校验。** 不引入配置框架，不允许多份配置漂移。
6. **ADR-006：检索层只交换 ScoredChunk。** Document 仅在 rerank 内部适配。

## 11. 最终判断

FastRag 的核心价值不在于「用了 LangGraph」或「用了 BM25 + 向量」，而在于它把一个小型 RAG 的**数据边界、失败边界和配置边界**讲清楚了：

- 数据从哪来、怎样校验、怎样重建；
- 哪一步失败可以降级，哪一步必须暴露；
- 哪些行为是配置，哪些是代码。

它现在最需要的不是更多功能，而是：

1. **测试**：证明改动没破坏行为；
2. **评测**：证明检索/回答确实变好；
3. **收敛**：让同一职责只有一处实现；
4. **观测**：让线上问题可定位。

按 Phase 0 → 1 → 2 走，它会从「一个读起来很舒服的项目」变成「一个敢长期维护的项目」。这比换任何框架都更有价值。
