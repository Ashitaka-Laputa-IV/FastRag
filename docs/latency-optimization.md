# RAG 链路时间优化建议

- 日期：2026-10-26
- 分支：`bench`
- 依据：本目录下 5 份基准报告 + `data/bench/` 的明细
- 口径：除特别说明外，耗时都是「到首 token」；历史报告里的 22 s 是「等完整回答」，两者不能直接比

## 0. 结论

1. **最大的一块是「思考」**：规划模型开着思考时，检索规划 6.9 s，占云端配置端到端的 91%；关掉后规划降到约 1.4 s。回答模型开着思考时，用户要等 20 s 以上才看到第一个字；关掉后云端约 0.5 s、本地约 1.5 s。
2. **模型换型不如关思考**：关思考后，本地 Qwen3-4B、DeepSeek-V4.1、Hunyuan-A13B、Qwen3.5-9B 的规划时间都落在 0.86–1.4 s，差距只有几百毫秒；真正的大头是固定成本。
3. **规划的输出本身约 1 s**：规划耗时减去模型首 token（约 0.03–0.4 s）后仍有约 1 s，几乎全是生成两条英文查询的时间。精简输出是关思考之后最值得做的一步。
4. **检索不是瓶颈**：BM25 20–26 ms，向量召回云端约 0.15 s、本地约 0.04 s，占端到端不到 2%；融合 0.1 ms，可以忽略。
5. **全本地已经可用**：bge-m3 + Qwen3-4B 全本地端到端中位数 2.5 s，比云端默认的 7.5 s 快 3 倍，且没有公网抖动（9 次极差 0.57 s vs 云端 8 s）。

### 2.3 规划时间拆解

规划 = 模型首 token + 生成两条查询。把直接测得的模型首 token 减掉，剩下的就是输出成本：

| 规划模型（关思考） | 规划耗时 | 模型首 token | 输出成本 |
| --- | ---: | ---: | ---: |
| 本地 Qwen3-4B | 1084 ms | 30 ms | ~1054 ms |
| DeepSeek-V4.1-Flash | 1404 ms | 411 ms | ~993 ms |
| Hunyuan-A13B | 1333 ms | 230 ms | ~1103 ms |
| Qwen3.5-9B | 1311 ms | 362 ms | ~949 ms |

**结论：关掉思考后换模型只能省几百毫秒；规划真正花时间的是「写两条查询」这个输出过程。**

## 3. 优化项

按「收益 / 改动成本」排序。收益都基于上面的实测值推算，标注了「实测」或「估算」。

### 3.1 关闭规划模型的思考（收益最大，1 行配置）

- **证据**：同一个 DeepSeek-V4.1-Flash，开思考规划 6937 ms，关思考 1404 ms（实测）。
- **改动**：

  ```toml
  [llm.route]
  thinking = false
  ```

- **预计收益**：云端端到端 7.5 s → 约 2.0 s（按 1404 + 142 + 491 估算），**-73%**。
- **风险**：规划质量未评测。上一轮 18 次里有 1 次 `need_search` 误判，无法确认与思考开关的因果关系；上线前应补一轮小样本质量检查。

### 3.2 关闭回答模型的思考（决定用户多久看到第一个字）

- **证据**：RAG 真实提示词下，DeepSeek 开着思考要 **23.7 s** 才吐出第一个正文字符（期间 1422 个空 chunk）；关掉后云端首 token 491 ms、本地 1454 ms（实测）。
- **改动**：

  ```toml
  [llm.answer]
  thinking = false
  ```

- **预计收益**：用户可见的首字延迟从 20 s 级降到 0.5–1.5 s 级。这是**体感收益最大**的一项，比任何检索或融合优化都重要。
- **风险**：回答质量与推理深度会下降，本文没有做质量评测；建议对事实类问题抽样对比再决定。

### 3.3 精简规划输出（关思考后最值得做的代码改动）

- **证据**：2.3 节显示，规划里约 1 s 花在生成两条完整英文查询上，模型首 token 只占 0.03–0.4 s。
- **可选改法**（任选其一）：
  1. 先只让模型判断 `need_search`（输出一个布尔值），需要检索时再单独生成一条短查询 —— 代价是多一次往返，但每次输出都短；
  2. 保留一次调用，但要求 `bm25_query` 用 3–5 个词、`vector_query` 不超过 12 个词，并去掉「必须写成完整问句」的要求；
  3. 直接从原始问题派生 BM25 查询（关键词规则），只让模型写向量查询。
- **预计收益**：输出 token 减半以上，规划预计从 1.0–1.4 s 降到 0.5–0.8 s（**估算**，需实测）。
- **风险**：查询变短可能降低召回质量；改完要用同一批问题对比 top-5 来源是否仍然相关。

### 3.4 本地或混合部署

| 方案 | 端到端（首 token） | 说明 |
| --- | ---: | --- |
| 云端默认（规划开思考、回答关思考） | 7496 ms（实测） | 当前配置 |
| 云端 + 规划关思考 | ~2000 ms（估算） | 3.1，改动最小 |
| 本地规划 + 云端回答 | **~1500 ms（估算）** | 规划 863 + 召回 42–142 + 首 token 491 |
| 全本地 | **2508 ms（实测）** | 无公网依赖、抖动最小 |

- 本地规划用 `qwen3-4b-instruct`，规划中位数 863 ms（实测），比云端关思考的 1404 ms 还快。
- 本地的短板在回答：4B 处理 3–4k token 上下文，首 token 1.45 s，比云端 0.49 s 慢。
- **推荐**：能常驻本地服务时，用「本地规划 + 云端回答」；完全离线或要稳定性时，用全本地配置 `config/fastrag.local.toml`。
- **风险**：本地服务需要常驻（`esl start bge-m3`、`esl start qwen3-4b-instruct`），机器负载变化会影响结果。

### 3.5 本地嵌入

- **证据**：召回从云端的 142 ms 降到本地 42 ms（实测）；向量查询 12 ms、BM25 20–26 ms。
- **改动**：`config/fastrag.local.toml` 里 `[embedding] endpoint = "local_embed"`、`dimensions = 1024`；一次性嵌入 2625 个 chunk 约 155 s。
- **预计收益**：端到端约 **-0.1 s**，更多收益在「不依赖公网」。
- **风险**：bge-m3（1024 维）与云端 Qwen3-Embedding-4B（2560 维）的检索质量未做量化对比，只抽查了一条查询。

### 3.6 缩小送入生成的上下文

- **证据**：全本地首 token 1.45 s，主要成本是约 3–4k token 的上下文预填充；直接测短提示词只要 30 ms。
- **改动**：`retrieval.top_n` 从 5 降到 3，或加大 `chunk_size` 减少碎片。
- **预计收益**：本地首 token 预计 **-0.3–0.6 s**（估算）；云端收益较小（-0.1–0.2 s）。
- **风险**：上下文变少可能影响回答完整度，需要质量抽检。

### 3.7 缓存规划结果

- **证据**：规划是纯函数（问题 → 查询），重复问题会重复付出约 1 s。
- **改动**：对 `plan_search` 的结果做缓存（问题归一化后作为 key，TTL 可设为小时级）。
- **预计收益**：命中时规划接近 0 ms；只对重复问题有效，适合文档问答这种问题高度集中的场景。
- **风险**：缓存过期后可能返回过时查询；需要失效策略。

### 3.8 不建议再做的事

- **融合**：RRF 实测 0.1 ms，优化没有意义（rerank 已经从 2.3 s 换成它）。
- **全量 rerank**：如果确实需要重排质量，用「RRF top 10 → rerank」，实测约 0.24 s（复用连接），不要回到 35 条全量重排。
- **继续拆 LLM 调用**：合并「路由 + 重写」的实测收益是 -1.5%（在噪声内），再拆回去只会增加往返；要省时间就减输出、关思考。
- **只换模型**：关思考后各家规划差距只有几百毫秒，换型解决不了 90% 的固定成本。

## 4. 推荐方案

| 场景 | 方案 | 预期端到端 | 主要代价 |
| --- | --- | ---: | --- |
| 改动最小、仍用云端 | 3.1 + 3.2：两个角色都 `thinking = false` | ~2.0 s（估算） | 回答深度下降，需质量抽检 |
| 追求最低延迟 | 3.4 混合：本地规划 + 云端回答 | ~1.5 s（估算） | 需要本地常驻服务 |
| 完全离线 / 稳定优先 | `--config config/fastrag.local.toml` | 2.5 s（实测） | 4B 回答质量与完整度 |
| 质量优先 | 保持开思考，只做 3.3 + 3.6 | 5–7 s（估算） | 仍是秒级等待 |

## 5. 验证方法与口径

```bash
# 云端（默认配置）
uv run python -m fastrag.bench --runs 5

# 云端 + 关思考
uv run python -m fastrag.bench --runs 5 --no-route-thinking

# 全本地
uv run python -m fastrag.bench --config config/fastrag.local.toml --runs 5

# 只测模型首 token（不经过链路）
uv run python -m fastrag.llm_ttft --runs 5
```

- 统一用「到首 token」口径（`bench.py` 默认），历史数据里 22 s 的「完整回答」不要混进来比较。
- 每组至少 5 次，看中位数与极差；云端单次结果不可信（同一模型曾出现 87 s → 544 ms）。
- 每次改完只动一个变量，并保留明细分到 `data/bench/`，不要覆盖旧文件。

## 6. 还没验证的部分

- **质量**：所有数字都只关于时间。关思考、换 4B、bge-m3、top_n 变小，都没有做答案正确性 / 召回质量评测。
- **长上下文**：`llm-ttft.md` 测的是短提示词；真实 RAG 上下文的预填充成本只在链路里体现（本地首 token 1.45 s）。
- **并发**：本地 llama.cpp 单实例没有并发测试，多用户排队未评估。
- **缓存**：3.7 只有方案，没有实测命中率与收益。
- **硬件**：本地数据来自这一台机器（i7-11800H / 22 GB），换机器、换量化都会变。
