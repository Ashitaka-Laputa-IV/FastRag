# 首 token 延迟基准：全云 / 全本地 / 混合

- 日期：2026-10-27
- 分支：`bench`
- 目标：回答「用户最快多久能看到第一个字」，对比三种部署方案
- 口径：从发出问题到生成节点吐出第一个 token（含检索规划、召回、融合）
- 样本：8 个问题 × 每个问题 5 次 = 每个方案 40 次

## 一页结论

| 方案 | 用户首字中位数 | 用户首字 P90 | 成功率 | 评价 |
| --- | ---: | ---: | ---: | --- |
| **全本地** | **1918 ms** | **2237 ms** | **40/40** | 最快、最稳，没有公网依赖 |
| 混合 | 2405 ms | 9520 ms | 36/40 | 中位数接近本地，但远端回答有长尾 |
| 全云 | 4170 ms | 13511 ms | 37/40 | 本次测量窗口内最慢，受远端嵌入与模型拥塞影响 |

- **全本地是本次唯一 100% 成功、且 40 次全部在 3 秒内完成的方案**。
- 混合方案的中位数只比本地慢约 0.5 秒，但 P90 被远端回答拖到 9.5 秒。
- 全云方案的两条远端依赖（嵌入 + 模型）同时波动：37 次成功里有 17 次召回超过 1 秒、13 次超过 4 秒。
- 如果只看「回答模型自己的首 token」：全云 553 ms、全本地 1047 ms、混合 1373 ms；差距主要不在模型，而在链路前端。

## 1. 测试设计

### 1.1 三个方案

| 环节 | 全云 | 全本地 | 混合 |
| --- | --- | --- | --- |
| 检索规划 | SiliconFlow `DeepSeek-V4.1-Flash`（关思考） | 本地 `qwen3-4b-instruct` | 本地 `qwen3-4b-instruct` |
| 回答 | SiliconFlow `DeepSeek-V4.1-Flash`（关思考） | 本地 `qwen3-4b-instruct` | SiliconFlow `DeepSeek-V4.1-Flash`（关思考） |
| 嵌入 / 召回 | SiliconFlow `Qwen3-Embedding-4B`（2560 维） | 本地 `bge-m3`（1024 维） | 本地 `bge-m3`（1024 维） |
| 融合 | RRF（k=60，权重 1.1/1.0） | 同左 | 同左 |
| 配置文件 | `config/fastrag.cloud.toml` | `config/fastrag.local.toml` | `config/fastrag.hybrid.toml` |

- 三个方案的语料、切块、BM25 索引、`top_n = 5` 完全一致，只换模型与嵌入。
- 两个云端模型都显式关闭思考（`enable_thinking = false`），避免推理 token 干扰首字延迟。
- 本地服务：`bge-m3` 在 `127.0.0.1:9931`，`qwen3-4b-instruct` 在 `127.0.0.1:9938`（llama.cpp）。

### 1.2 问题集

8 个中文问题，全部指向 LangChain / LangGraph 官方文档：

1. LangGraph 中如何实现 human-in-the-loop？
2. 如何让 LangGraph 的图流式输出 token？
3. LangChain 的 Agent 如何调用工具？
4. LangGraph 如何用 checkpointer 持久化会话状态？
5. LangChain 如何搭建 RAG 检索链？
6. LangGraph 的条件边（conditional edges）怎么用？
7. LangChain 的文本分割器怎么选？
8. LangGraph 如何实现子图与并行分支？

整轮开始前用第一个问题预热 1 次（不计入统计），随后 8 个问题各跑 5 次。

### 1.3 两个时间指标

- **用户首字**：从发出问题到第一个回答 token，等于 `检索规划 + 召回 + 融合 + 回答首 token`。这是报告的主指标。
- **回答首 token**：只有生成阶段，衡量「资料准备好之后，模型多快开口」。用来区分瓶颈在链路还是模型。

运行时直连云端（清空代理变量），本地服务全程在线；语料 2625 个 chunk，向量均复用已有缓存。

## 2. 总体结果

### 2.1 主指标：用户首字

| 方案 | 中位数 | 平均 | P90 | 最小 | 最大 | 2 秒内完成 | 3 秒内完成 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 全本地 | **1918 ms** | 1896 ms | **2237 ms** | 891 ms | 2370 ms | 25/40 | **40/40** |
| 混合 | 2405 ms | 5327 ms | 9520 ms | 1199 ms | 33685 ms | 8/36 | 23/36 |
| 全云 | 4170 ms | 6169 ms | 13511 ms | 1865 ms | 18882 ms | 1/37 | 16/37 |

### 2.2 回答首 token

| 方案 | 中位数 | 平均 | P90 | 最小 | 最大 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全云 | **553 ms** | 1313 ms | 2340 ms | 385 ms | 8770 ms |
| 全本地 | 1047 ms | 931 ms | 1175 ms | 54 ms | 1222 ms |
| 混合 | 1373 ms | 4381 ms | 8738 ms | 407 ms | 32704 ms |

> 本地最小 54 ms 是 llama.cpp 的 prompt cache 命中（同一问题、同一上下文）；40 次里有 3 次低于 100 ms，剔除后中位数 1079 ms。这不影响「全本地最稳」的结论。

### 2.3 阶段拆解（中位数）

| 阶段 | 全云 | 全本地 | 混合 |
| --- | ---: | ---: | ---: |
| 检索规划 | 1640 ms | 931 ms | 900 ms |
| 召回 | 268 ms | 37 ms | 34 ms |
| 融合 | 0.1 ms | 0.1 ms | 0.1 ms |
| 回答首 token | 553 ms | 1047 ms | 1373 ms |
| **用户首字** | **4170 ms** | **1918 ms** | **2405 ms** |

> 各阶段中位数不能直接相加：同一组数据里各阶段的尖峰落在不同运行上，所以「用户首字」是逐次计时后的中位数，不是上表四行之和。

- 全云的规划比本地慢约 0.7–0.8 秒，召回慢约 0.23 秒，回答反而最快。
- 全本地的回答是最慢的一环（1.05 秒），但前端只要约 0.97 秒，整体仍然最短。
- 混合把前端压到 0.93 秒，却把回答交给云端，首 token 中位数 1.37 秒，整体居中。
- 同样是 DeepSeek 回答，全云里 0.55 秒、混合里 1.37 秒，差异来自送入的上下文不同以及测量窗口的波动，不是模型本身变了。

## 3. 分问题结果

用户首字中位数（每个问题 5 次）：

| 问题 | 全云 | 全本地 | 混合 |
| --- | ---: | ---: | ---: |
| Q1 human-in-the-loop | 3018 ms | 2226 ms | 4504 ms |
| Q2 流式输出 token | 5122 ms | 1824 ms | 2199 ms |
| Q3 Agent 调用工具 | 6758 ms | 1920 ms | 2483 ms |
| Q4 checkpointer 持久化 | 8882 ms | 925 ms | 2198 ms |
| Q5 搭建 RAG 检索链 | 2821 ms | 1795 ms | 3155 ms |
| Q6 条件边 | 4170 ms | 1916 ms | 1839 ms |
| Q7 文本分割器 | 3021 ms | 1992 ms | 2924 ms |
| Q8 子图与并行分支 | 2289 ms | 2001 ms | 2155 ms |

- 全本地每题都在 0.9–2.3 秒，问题之间差异最小。
- 全云波动最大：Q4 到 8.9 秒，Q8 只要 2.3 秒，差异来自远端召回与模型的排队。
- 混合在 Q1 出现 4.5 秒，主要是一次远端回答的首 token 拖慢。

## 4. 稳定性与失败

| 指标 | 全云 | 全本地 | 混合 |
| --- | ---: | ---: | ---: |
| 成功 / 尝试 | 37 / 40 | **40 / 40** | 36 / 40 |
| 失败原因 | 429 限流 3 次 | 无 | 429 限流 4 次 |
| 召回 > 1 s 的次数 | 17 / 37 | 0 / 40 | 0 / 36 |
| 召回 > 4 s 的次数 | 13 / 37 | 0 / 40 | 0 / 36 |
| 用户首字极差 | 17.0 s | 1.5 s | 32.5 s |

- 全云的所有异常都来自远端：3 次失败是 429 限流，13 次超长召回是远端嵌入超过 4 秒；同一窗口内本地嵌入稳定在 25–56 ms。
- 混合的失败与长尾都来自远端回答：同一窗口里本地召回最大 70 ms、规划最大 1.1 s，两者都没出现秒级尖峰。
- **全云方案同时依赖两个远端服务，任意一个拥塞都会直接反映到用户等待时间**。

## 5. 怎么解读

1. **全本地适合「确定性优先」**：40 次全部成功、P90 2.24 秒、最慢 2.37 秒；代价是回答由 4B 模型生成，质量未评测，首 token 约 1 秒。
2. **混合适合「质量与速度折中」**：中位数 2.4 秒，回答质量沿用云端模型；但远端回答在本次窗口出现 9–33 秒的长尾，需要超时与降级策略。
3. **全云在当前网络与厂家负载下并不快**：模型首 token 只有 0.55 秒，但前端（规划 1.6 秒 + 召回 0.27 秒，且常有数秒尖峰）把总时间推到 4.2 秒。
4. **嵌入的位置比模型更影响稳定性**：把嵌入换到本地，召回从「中位 0.27 秒、P90 7.7 秒」变成「中位 0.03 秒、最大 0.06 秒」。如果只能改一处，先本地化嵌入。
5. **不要只看中位数**：混合的中位数 2.4 秒看起来不错，但 P90 是 9.5 秒；全本地的中位数与 P90 只差 0.3 秒。

## 6. 建议

- **默认推荐全本地**（`config/fastrag.local.toml`）：如果 4B 的回答质量可接受，它在速度和稳定性上全面领先。
- **需要云端回答质量时用混合**（`config/fastrag.hybrid.toml`）：但必须给回答节点加超时（建议 3 秒）并在超时后回退到本地模型，否则会偶发 10 秒级等待。
- **不建议继续用全云作为默认**：除非能接受规划 1.6 秒、召回偶发 4–15 秒、以及约 8% 的限流失败。
- **下一步优化顺序**：本地化嵌入 → 本地化规划 → 回答侧超时/降级 → 再考虑换更快的云端模型。
- 所有涉及关闭思考的结论仅针对延迟；回答质量需要单独评测。

## 9. 局限

- 云端与混合的测量窗口内，SiliconFlow 明显拥塞（429、嵌入 4–15 秒）；这放大了全云的劣势，但「远端依赖会带来长尾」的结论不受影响。换时间复测，全云的中位数可能更接近 2–3 秒。
- 每题 5 次、共 40 次，尾部估计仍不精确；长尾次数（如 13 次 >4 秒）受窗口影响。
- 本地问答会命中 llama.cpp 的 prompt cache（3/40 次 <100 ms），同问题重复测量的本地首 token 略偏乐观。
- 只测到首 token，没有评估回答质量、完整回答耗时与幻觉率；4B 与 DeepSeek 的质量差异需要单独评测。
- 本地向量（bge-m3 1024 维）与云端（Qwen3-Embedding-4B 2560 维）的检索质量未做量化对比。
- 所有数据来自同一台机器（Intel i7-11800H / 22 GB），换机器、换量化都会变化。
