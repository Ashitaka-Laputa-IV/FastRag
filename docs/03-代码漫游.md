## 2. 入口：从命令行到 Config

### 2.1 两个入口

`pyproject.toml` 里：

```toml
[project.scripts]
fastrag = "fastrag.cli:main"
```

所以 `fastrag ...` 最终调用 `src/fastrag/cli/__init__.py` 暴露的 `main`。`python -m fastrag` 则走：

```python
# __main__.py
from fastrag.cli import main

if __name__ == "__main__":
    raise SystemExit(main())
```

### 2.2 `cli/main.py` 做了什么

`main()` 的实际顺序是：

```text
_extract_globals（同时把 --config/-v/--version 从任意位置抽出来）
  → if globals.version: 打印版本，return 0
  → _configure_logging(globals.verbose)
  → _build_parser() + parse_args(rest)
  → 没有子命令: print_help，return 0
  → load_env()
  → _load(globals.config)（resolve_config + load_config）
  → args.handler(args, config)
  → 捕获 FastragError / KeyboardInterrupt，转成退出码
```

几个容易忽略的点：

- `--version` 在 `_extract_globals` 内部就被识别，先于 logging 和 argparse；
- `_extract_globals` 允许 `fastrag --config local search ...` 和 `fastrag search ... --config local` 两种写法；
- `load_env()` 在配置加载之前调用，所以 `.env` 里的 key 对后续 `endpoint_api_key` 可见；
- 子命令模块只提供 `add_parser` 与 `run(args, config)`，不自己解析全局参数；
- 退出码不是统一的 1：`_extract_globals` 的 `FastragError` 返回 2，argparse 参数错误也以 2 退出；`load_env`/`_load`/handler 的 `FastragError` 返回 1；`KeyboardInterrupt` 返回 130；正常或无子命令返回 0。

### 2.3 配置加载：先定位，再解析路径

`config/loader.py` 的核心是三个函数：

```python
home()                 # 数据与 .env 的根
default_config_ref()   # 默认配置来源
resolve_config(value)  # --config 的值 → ConfigRef
```

`home()` 的优先级：

```text
FASTRAG_HOME
  > 源码树根（存在 pyproject.toml）
  > 当前工作目录
```

这解释了为什么在 editable 工作区里跑 CLI，`data/` 会落在仓库根目录；装成 wheel 后则落在你执行命令的目录。

`resolve_config()` 的顺序：

```text
该值作为路径存在 → 当路径
否则 value == "default" → default_config_ref()
否则包内 config/fastrag.<value>.toml
否则 FastragError
```

`default_config_ref()` 只看 `$FASTRAG_HOME/config/fastrag.toml`（存在就用），否则用包内模板；它**不会读取 `FASTRAG_CONFIG`**。因此 `--config default` 与不传 `--config` 在设置了 `FASTRAG_CONFIG` 时行为不同。另外，如果当前目录恰好有名为 `default` 的同名路径，`resolve_config()` 会先把它当路径。

注意：**路径判断是相对当前工作目录，不是相对 `FASTRAG_HOME`。** 只有 `[paths]` 和 `.env` 是相对 `FASTRAG_HOME`。

`load_config()` 本身不读 `.env`。它的顺序是：

```text
显式 ref > 显式 path > FASTRAG_CONFIG > default_config_ref()
```

CLI 的 `--config` 走的是显式 `ref`；不传时才落到 `FASTRAG_CONFIG` 和默认配置。

读取 TOML 后，先把 `[paths]` 的每个值拼到 `home()` 下并 `resolve()`，再交给 pydantic。这样 `Config` 里的路径都是绝对路径，后续代码不需要再关心工作目录。

### 2.4 配置模型：加载即校验

`config/models.py` 的 `_Strict` 基类做了两件事：

```python
model_config = ConfigDict(extra="forbid", frozen=True)
```

- 拼错键、少写必填项 → 加载时报错；
- 实例不可重新赋值，避免运行中被意外修改。

跨字段校验分散在各节的 model_validator 和 `Config._check_endpoints` 中，例如：

- `Chunking._check`：`chunk_overlap < chunk_size`，`boilerplate_pattern` 必须是可编译的正则；
- `Fusion._check_weights`：`weights` 必须包含 `bm25` 与 `vector`，且值为正；
- `Config._check_endpoints`：`llm.route` / `llm.answer` 的 fallback 链上每个 endpoint 都必须在 `[endpoints]` 里存在。

这一步是「配置错误尽早暴露」的关键。没有它，很多问题会拖到第一次检索或第一次调用 LLM 才出现。

## 3. 路线 A：`fastrag prepare`

### 3.1 命令层

`prepare` 不包含下载：它从 `data/langchain-docs/` 里已有的 Markdown 开始。空目录时 `iter_docs` 会提示先运行 `fastrag download`。

`cli/commands/prepare.py` 只有三十多行：

```python
def run(args, config):
    print("[1/3] 切块")
    if chunk_command.run(args, config) != 0:
        return 1

    print("[2/3] 嵌入向量")
    store = ChunkStore.load(config)
    ensure_vectors(config, store)

    print("[3/3] BM25 索引")
    build_index(config, store)
    return 0
```

它自己不实现任何业务，只负责顺序与失败短路。这是 CLI 层的正确写法。

### 3.2 切块：从 Markdown 到 `chunks.jsonl`

`cli/commands/chunk.py` 调用 `ingest/chunker.py`：

```text
build_chunks(config)
  → iter_docs(config)                   排序递归遍历 *.md
  → strip_boilerplate(text, pattern)    去掉站点模板头，返回正文 + 偏移
  → SentenceChunker(...)                按 token 切句
  → Chunk(id=..., source=..., start=..., end=..., text=..., token_count=...)
```

关键细节：

1. **source 通常是相对路径。** `display_path()` 把绝对路径转成相对 `FASTRAG_HOME` 的 POSIX 路径；如果文件在 home 外，则退回绝对路径。home 内的语料因此可迁移；home 外的绝对路径会绑死机器，这是例外。
2. **偏移要加回模板头长度。** `strip_boilerplate` 返回的是「正文起点」，`SentenceChunker` 的 piece 偏移是相对正文的，构造 `Chunk` 时要加上这个起点，才能保证 `text == 原文件[start:end]`。
3. **id 是内容寻址。** `chunk_id(source, text)` 把 source 和 text 一起哈希，所以同一段文字换个文件就是另一个 chunk。
4. **空语料直接失败。** 没有可切文档时 `chunk.run` 返回 1，`prepare` 随之中断，不会写出空文件。

`write_chunks()` 用临时文件 + `os.replace` 原子写整份 JSONL。注意它每次都是**全量重写**，不是追加。

### 3.3 `ChunkStore.load`：把真源读进来

`index/store.py` 做三件事：

```python
digest = file_sha256(chunks_file)  # 1 MiB 分块读，覆盖整个文件字节
chunks: list[Chunk] = []
with chunks_file.open(encoding="utf-8") as fh:
    for number, line in enumerate(fh, start=1):
        if not line.strip():
            continue
        chunks.append(Chunk.from_record(json.loads(line)))
```

- 摘要覆盖整个文件字节，任何空白/顺序变化都会改变 digest；
- 逐行解析，空行跳过，JSON/字段错误会带行号；
- `by_id` 是只读映射，防止下游偷偷改 store。

### 3.4 向量：复用、补嵌、归一化

`index/dense.py` 是建库期最复杂的一块。按执行顺序看：

```text
ensure_vectors(config, store, embeddings=None)
  → 如果 embeddings 为 None，build_embeddings(config)
  → current_ids = [chunk.id for chunk in store]
  → previous = _load_previous(config, store)
  → 如果 previous 存在且 ids 完全相同（含顺序）：直接返回旧矩阵
  → 如果 previous 存在但 ids 不同：按 id 复制可复用行，对缺失 id 调 embed_texts()
  → 如果 previous 为 None：全部视为缺失，全量嵌入
  → _normalize(矩阵)
  → 分别原子写 vectors.npy 与 manifest.json
```

`build_embeddings()` 的关键参数：

```python
OpenAIEmbeddings(
    model=config.embedding.model,
    base_url=...,
    api_key=...,
    chunk_size=config.embedding.batch_size,
    max_retries=config.embedding.max_retries,
    request_timeout=config.embedding.timeout,
    check_embedding_ctx_length=False,
)
```

`check_embedding_ctx_length=False` 是有意为之：它避免 LangChain 在客户端用 tiktoken 重新切分/校验文本，直接把原文交给端点。这要求端点自己处理上下文长度。

`embed_texts()` 会：

- 按 batch_size 分批；
- 每批校验返回条数与维度；
- 预分配 `(N, dimensions)` 的 float32 矩阵；
- 记录进度日志。

`_normalize()` 对每行做 L2 归一化，零向量用 `1e-12` 兜底。归一化后，内积就等于余弦相似度，查询时只需要一次矩阵乘法。

`_load_previous()` 的校验比很多人想象的宽松：

- 读 manifest；
- 校验模型、维度（**不校验 `normalized` 标记**）；
- 读 npy，校验为二维且行数与 ids 长度一致（**不校验列数是否等于配置维度**）；
- **不比较 source_digest**。

原因是 chunk id 已经内容寻址：只要新旧 ids 对得上，在目标规模下可视为文本没变（id 是 64 位截断哈希，碰撞概率可忽略）。写回与补嵌要分三种情况看：

1. `_load_previous()` 返回 `None`（没有 manifest/npy，或模型/维度不符，或 npy 不是二维、行数与 ids 长度不一致）：全量嵌入当前所有 chunk，并写回 `vectors.npy` 与 manifest；
2. 旧 ids 与当前 ids 完全相同（含顺序）：直接返回旧矩阵，不写盘，也不调用嵌入；manifest 里的 `source_digest` 不会刷新；
3. 旧 ids 不同：按 id 复用仍存在的行，只对缺失 id 调用 `embed_texts`，然后写回 npy 与 manifest；如果只是顺序变化、没有缺失 id，则只重写，不调用嵌入。

manifest 里的 `source_digest` 只是来源记录，不是复用条件。

### 3.5 BM25：全量重建，严格校验

`index/bm25.py` 的建库路径：

```text
build_index(config, store)
  → texts = [chunk.text for chunk in store]
  → tokens = bm25s.tokenize(texts, stopwords=...)
  → retriever = bm25s.BM25(method=config.bm25.method)
  → retriever.index(tokens)
  → retriever.save(index_dir, corpus=[chunk.id for chunk in store])
  → write meta.json（ArtifactKey）
```

检索路径：

```text
load_index(config, store)
  → check_index（meta 存在、kind/digest/params 匹配）
  → bm25s.BM25.load(index_dir, load_corpus=True)

search_bm25(...)
  → tokenize(query)
  → retrieve(k=min(k, len(corpus)))
  → 过滤 score <= min_score
  → 从 corpus 里取回 chunk id
  → store.by_id[id] 取 Chunk
  → ScoredChunk(channel="bm25")
```

几个实现细节：

- `save(corpus=[id...])` 让 bm25s 只存 id，不存正文；正文永远回 `ChunkStore` 取，避免两份真源；
- 如果 bm25s 把 corpus 包装成 dict，`raw.get("text", raw.get("id"))` 兼容两种形态；
- id 在 store 里找不到时只记 warning，不抛异常，避免一个坏索引让整次检索失败；
- `min_score` 是严格大于，默认 0 会过滤掉所有 0 分命中。

`meta.json` 的校验比向量严格得多：digest 或 method/stopwords 任何一项变化，都要求重新建索引。这是因为 BM25 的语料顺序、分词和参数强耦合，按 id 增量复用并不安全。

### 3.6 产物验收

`prepare` 结束后，建议手动检查：

```powershell
Get-Content data\chunks.jsonl -TotalCount 1
Get-ChildItem data\embeddings
Get-ChildItem data\bm25-index
```

- `chunks.jsonl` 第一行是否是合法 JSON，字段是否齐全；
- `manifest.json` 的 `count` / `ids` 长度是否与 chunks 数一致；
- `meta.json` 的 `source_digest` 是否与当前 chunks 文件摘要一致。

## 4. 路线 B：`fastrag ask`

### 4.1 构造 Pipeline：`__init__` 不做 I/O

`cli/commands/ask.py`：

```python
pipeline = RagPipeline.from_config(config)
while True:
    question = input("问题（回车退出）: ").strip()
    ...
    for event in pipeline.stream(question):
        ...
```

`RagPipeline.__init__` 只做三件事：

```python
self.resources = ResourceBundle(config)  # 只存 config
self.nodes = RagNodes(self.resources)
self.graph = build_graph(self.nodes)
```

`ResourceBundle` 的每个资源都是 `cached_property`，构造时不加载。`build_graph()` 只装配节点与边，也不加载资源。因此：

- `import fastrag` 无 I/O；
- `RagPipeline.__init__` 无 I/O；
- `RagPipeline.from_config(config)` 传入现成配置时只构造，不读盘；无参 `from_config()` 会调用 `load_config()` 读 TOML，但不读 `.env`；
- 第一次真正需要 store/vectors/BM25/LLM 时才加载。

### 4.2 资源懒加载的顺序

一次需要检索的问答，资源访问顺序大致是：

```text
plan_search
  → resources.prompts（读 3 份提示词）
  → resources.plan_chain（构建路由模型）
  → plan_chain.invoke

retrieve_bm25
  → resources.bm25（load_index → ChunkStore）
  → search_bm25

retrieve_vector
  → resources.embeddings（build_embeddings）
  → resources.vectors（ensure_vectors，可能写盘）
  → search_dense

fuse（rerank 模式）
  → resources.reranker（build_reranker）

answer
  → resources.prompts（已缓存）
  → resources.answer_chain（构建回答模型）
  → answer_chain.invoke
```

注意 `retrieve_vector` 的 `resources.vectors` 可能触发 `ensure_vectors`。如果你只跑了 `chunk` 没跑 `embed`，第一次 `ask` 会现场补向量，这既慢又会产生 API 费用。生产环境建议先 `warmup()` 预热索引类资源，或在启动时显式跑一次 `embed`。

`warmup()` 只加载 `store`、`vectors`、`bm25`（`rerank` 模式下再加 `reranker`），**不会**加载 prompt、`plan_chain`、`answer_chain`，因此也不能提前验证路由/回答端点的 key。第一次问答仍会构造 LLM 链。

### 4.3 `ask()` 与 `stream()` 的分叉

`RagPipeline.ask()` 走同步 `graph.invoke`：

```python
state = self.graph.invoke({"question": question})
return result_from_state(state, self._metadata(), elapsed)
```

`RagPipeline.stream()` 走 v3 `stream_events`：

```python
with warnings.catch_warnings():
    warnings.filterwarnings("ignore", message="Pydantic serializer warnings")
    warnings.filterwarnings(
        "ignore",
        message="The v3 streaming protocol on Pregel is experimental.",
    )
    run = self.graph.stream_events({"question": question}, version="v3")
    for stream in run.messages:
        if stream.node != "answer":
            continue
        for delta in stream.text:
            yield AnswerEvent(kind="token", text=delta)
    state = run.output or {}
yield AnswerEvent(kind="done", result=result_from_state(...))
```

几个事实：

- 只有 `answer` 节点的文本会变成 token；路由和检索不流式；
- `run.output` 是图执行完的最终 state；
- v3 协议目前是实验性的，所以代码显式抑制了相关警告；
- 正常完成时，`done` 是最后一个事件，携带完整 `AnswerResult`；如果图执行或事件迭代抛异常，生成器会直接结束，不保证发出 `done`。

### 4.4 `plan_search`：一次调用，两个查询

```python
prompt = _render(self.resources.prompts["search_plan"], question=...)
plan = self.resources.plan_chain.invoke(prompt)
```

`plan_chain` 是：

```python
build_with_fallbacks(
    lambda role: build_llm(role, config).with_structured_output(SearchPlan),
    config.llm.route,
)
```

所以模型返回的是 `SearchPlan` 对象，不是自由文本。节点随后做三件事：

1. `plan is None` 或调用异常 → `_degrade_route`；
2. `need_search=False` → 清空两路查询；
3. 否则逐路 `strip()`，空字符串回退为原问题。

`_degrade_route` 的行为是：

```python
{
    "plan": None,
    "need_search": True,
    "bm25_query": question,
    "vector_query": question,
}
```

这体现了一个产品判断：**路由失败时宁可多检索，也不要直接放弃资料。**

### 4.5 两路并行召回

`route_after_plan` 返回一个列表：

```python
if not need_search:
    return ["answer"]
return ["retrieve_bm25", "retrieve_vector"]
```

在 LangGraph 里，返回多个节点名表示同一超步内并行执行。两个节点都写入 state 的不同键（`bm25` / `vector`），所以不会互相覆盖。

`retrieve_bm25`：

```python
search_bm25(
    self.resources.bm25,
    self.resources.store,
    self.config,
    state["bm25_query"],
    self.config.retrieval.bm25_candidates,
)
```

`retrieve_vector`：

```python
search_dense(
    self.resources.embeddings,
    self.resources.vectors,
    self.resources.store,
    state["vector_query"],
    self.config.retrieval.vector_candidates,
)
```

两路都返回 `list[ScoredChunk]`，只是 `channel` 不同。

### 4.6 `fuse`：RRF 或 rerank

```python
bm25 = state.get("bm25", [])
vector = state.get("vector", [])
if not bm25 and not vector:
    return {"fused": []}
rankings = {"bm25": bm25, "vector": vector}
```

如果 `fusion.method == "rerank"`：

```python
merged = self._merge(bm25, vector)  # 按 id 去重，保留先出现
query = state.get("vector_query") or state["question"]
fused = rerank_chunks(self.resources.reranker, query, merged, top_n)
```

- 合并顺序是 BM25 在前、向量在后；
- 重复 id 只保留第一次出现的那条；
- 重排查询优先用 `vector_query`，因为它更接近自然语言；
- 重排返回的 `ScoredChunk.channel = "rerank"`；
- 任何异常都会 warning 并退回 `_fuse_rrf(rankings)`。

RRF 路径：

```python
fused = rrf_fuse(rankings, config.fusion.rrf_k, config.fusion.weights)
return fused[: config.retrieval.top_n]
```

`rrf_fuse` 的公式是 `Σ weight / (k + rank)`，`rank` 从 1 开始，按传入列表的 `enumerate` 计算。它不使用 `ScoredChunk.rank` 字段，也不比较原始分数。

### 4.7 `answer`：拼上下文，调模型

```python
if state.get("need_search", True):
    limit = config.retrieval.context_chunks or config.retrieval.top_n
    chunks = state.get("fused", [])[:limit]
    context = self._context(chunks)
    prompt = _render(self.resources.prompts["answer"], context=context, question=...)
else:
    prompt = _render(self.resources.prompts["chat"], question=...)
return {"answer": self._answer_text(prompt)}
```

`_context()` 的格式：

```text
[1] data/langchain-docs/....md
<chunk 正文>

[2] ...
```

没有命中时是 `（无检索结果）`。`_answer_text()` 捕获所有异常，记录 error，返回空串；这样单轮失败不会让交互循环退出。

### 4.8 组装 `AnswerResult`

```python
sources = tuple(state.get("fused") or ())
plan = state.get("plan")
metadata = dict(base_metadata)
metadata["elapsed_seconds"] = round(elapsed, 3)
metadata["need_search"] = bool(state.get("need_search", True))
metadata["queries"] = {
    "bm25": state.get("bm25_query", ""),
    "vector": state.get("vector_query", ""),
}
```

`base_metadata` 来自 `RagPipeline._metadata()`：

```python
{
    "model": config.llm.answer.model,
    "provider": config.llm.answer.provider,
    "fusion": config.fusion.method,
    "prompt_sha": resources.prompt_hashes,
}
```

注意 `sources` 是**融合后的全部结果**（最多 `top_n` 条），不是只进入回答提示词的那几条；`context_chunks` 只影响 `answer` 节点看到的内容，且实际条数是 `min(context_chunks, top_n)`。

### 4.9 CLI 怎样打印

`cli/commands/ask.py` 的事件循环：

- `kind == "token"`：直接写 stdout 并 flush；
- `kind == "done"`：
  - 如果本轮一个 token 都没打印，打印 `result.answer` 或「（本轮没有生成回答）」；
  - 如果打印过 token，补一个换行；
  - 如果 `need_search`，打印 BM25/向量查询；
  - 否则打印「未检索本地文档」；
  - 遍历 `result.sources`，打印 `来源: source#start-end`。

它不打印分数和通道，因为交互问答更关心「答案 + 出处」；调试分数请用 `search` / `rrf` / `rerank`。

## 5. 路线 C：调试命令

这些命令绕过 LangGraph，直接组合底层函数，适合定位「是检索问题还是生成问题」。

| 命令 | 调用链 | 是否联网 |
| --- | --- | --- |
| `search "..." -k 5` | `ChunkStore → load_index → search_bm25 → format_hits` | 否 |
| `embed --query "..."` | `ChunkStore → build_embeddings → ensure_vectors → search_dense` | 建向量/查询时是 |
| `index` | `ChunkStore → build_index` | 否 |
| `rerank "..." -n 5` | `ChunkStore → load_index → search_bm25 → build_reranker → rerank_chunks` | 重排时是 |
| `rrf "..." -n 5` | `ChunkStore → build_embeddings → ensure_vectors → load_index → 两路 search → rrf_fuse` | 查询嵌入时是 |

`rrf` 命令还会打印每个命中在两路里的原始名次：

```text
1. 0.0328  data/langchain-docs/...#120-480  (bm25 #1 / vector #3)
```

这对调权重非常有用：如果某个通道长期没有贡献，可以考虑调低权重或检查该通道的召回。

## 6. 失败与降级：读代码时重点看 `try`

### 6.1 路由失败

位置：`nodes.plan_search`。

```python
try:
    plan = self.resources.plan_chain.invoke(prompt)
except Exception as exc:
    return self._degrade_route(state, ...)
```

捕获的是「所有异常」，包括模型服务错误、结构化输出解析失败、fallback 链全部失败。降级结果是「用原问题检索两路」。

### 6.2 重排失败

位置：`nodes.fuse`。

```python
try:
    fused = rerank_chunks(...)
except Exception as exc:
    logger.warning(...)
    return {"fused": self._fuse_rrf(rankings)}
```

降级后 `channel` 是 `rrf`，不是 `rerank`。调用方如果依赖 `channel` 判断「是否用了重排」，要以这个为准。

### 6.3 回答失败

位置：`nodes._answer_text`。

```python
try:
    return self.resources.answer_chain.invoke(prompt)
except Exception as exc:
    logger.error(...)
    return ""
```

它不会把异常抛给图；最终 `AnswerResult.answer` 是空串。CLI 会打印「本轮没有生成回答」。库调用方应该检查 `result.answer` 是否为空。

### 6.4 检索失败

`retrieve_bm25` / `retrieve_vector` 没有 try。索引损坏、嵌入维度不符、文件缺失等异常会直接抛出图，最终由 CLI 的 `ask` 循环捕获（单轮失败）或库调用方处理。

这是一个有意的边界：**检索是数据正确性问题，不应该静默降级成空结果。** 否则用户会得到「模型说没找到」的假象。

## 7. 扩展点：改哪里，不改哪里

### 7.1 新增一个 CLI 命令

1. 在 `cli/commands/` 新建模块，提供：

   ```python
   def add_parser(subparsers): ...
   def run(args, config) -> int: ...
   ```

2. 在 `cli/commands/__init__.py` 的 `COMMANDS` 元组里注册；
3. 业务逻辑放在下层模块，命令层只做参数与打印。

不要在新命令里重新实现一套检索编排；优先复用 `index` / `retrieve` 的函数。

### 7.2 新增一个配置字段

1. 在 `config/models.py` 对应模型里加字段，给默认值或设为必填；
2. 在 `resources/config/fastrag.toml` 与 `fastrag.local.toml` 里同步；
3. 在使用它的模块里读取 `config.xxx`；
4. 如果影响产物，更新 `ArtifactKey` 的 params 与校验逻辑。

`extra="forbid"` 只拦截未知键：新增**必填**字段时，旧 TOML 缺字段会加载失败；新增**有默认值**的可选字段时，旧 TOML 会自动使用默认值，不会报错。所以同步 TOML 主要是为了显式记录默认值和示例，而不是靠校验强制。

### 7.3 新增/修改提示词

- 包内默认：`src/fastrag/resources/prompts/<name>.txt`；
- 用户覆盖：`$FASTRAG_HOME/prompts/<name>.txt`；
- 占位符是 `string.Template` 的 `$name`，不是 `str.format` 的 `{name}`；
- 新增提示词时，记得把名字加进 `ResourceBundle.PROMPT_NAMES`，否则不会被加载和哈希。

当前渲染用 `safe_substitute`：未知占位符会原样保留，不会报错。改提示词时要特别小心拼写；这也是第 04 篇建议改成严格渲染的原因之一。

### 7.4 换模型 / 换端点

只需要改 TOML：

```toml
[endpoints.my_endpoint]
base_url = "https://.../v1"
api_key_env = "MY_KEY"

[llm.answer]
endpoint = "my_endpoint"
model = "my-model"
provider = "openai"
```

保持 `provider = "openai"`：当前所有端点都走 OpenAI 兼容协议。`thinking`、`extra_body`、`retries`、`timeout` 都在角色级配置；`retries` 会映射到 SDK 的 `max_retries`。注意 `[embedding]` 用的是 `max_retries`，字段名不同。

### 7.5 新增一个检索通道

这不是「加一个函数」那么简单，至少要改：

1. `domain.ScoredChunk.channel` 的新值；
2. `index/` 里新增检索函数，返回 `ScoredChunk`；
3. `RagState` 增加字段，`RagNodes` 增加节点，`graph.py` 增加边；
4. `cli/commands/rrf.py` 的 `rankings` / `positions` 组装；
5. 评估该通道的候选数、分数尺度与失败模式；
6. 视需要决定是否把它接入 RRF 权重；`Fusion._check_weights` 只要求 `bm25`/`vector` 存在，额外通道本来就被允许，`format_hits` 也不打印 channel，通常不必改。

如果只是实验，建议先在 CLI 里拼一个原型，不要直接改图。

### 7.6 新增一种派生产物

1. 定义新的 `kind`；
2. 用 `ArtifactKey(kind, source_digest, params)` 写 manifest/meta；
3. 加载时校验；
4. 单文件用临时文件 + `os.replace` 原子写；如果产物是目录（像 BM25 索引），要么接受 `bm25s.save` 式的直接写入，要么先写临时目录再整体替换；
5. 想清楚「语料变化时是全量重建还是按 id 增量」。

参考 `index/dense.py` 与 `index/bm25.py` 的两种强度：向量按 id 复用，BM25 严格校验后全量重建。

## 8. 阅读顺序与调试技巧

### 8.1 三种读法

**20 分钟版：**

```text
README
  → domain.py
  → pipeline/graph.py
  → pipeline/nodes.py
  → 02 篇的不变量
```

**2 小时版：**

```text
03 篇路线 A + B
  → pipeline/resources.py
  → index/dense.py
  → index/bm25.py
  → config/loader.py
```

**深入版：**

```text
config/models.py
  → ingest/chunker.py
  → ingest/artifacts.py
  → retrieve/fusion.py
  → retrieve/rerank.py
  → llm/client.py
  → cli/main.py
```

### 8.2 调试技巧

- 先用 `fastrag search` 确认 BM25 有没有命中；没有命中就不是 LLM 的问题。
- 用 `fastrag rrf` 看两路名次；如果向量一路全是 `-`，检查嵌入是否建好、查询是否为空。
- 用 `fastrag rerank` 单独验证重排端点；如果它报错，`ask` 会自动降级 RRF。
- 打开 `-v` 看 warning/error 日志，尤其是「路由模型全部失败」「重排失败」。
- 在 Python REPL 里直接构造 `ResourceBundle(config)`，逐个访问 `store` / `vectors` / `bm25`，能把懒加载的失败点定位得很清楚。
- 检查 `AnswerResult.metadata["queries"]`，确认路由到底给了什么查询；如果两条都等于原问题，可能是路由降级了。

### 8.3 不要做的事

- 不要在 `pipeline` 里直接 `open()` 数据文件；走 `ResourceBundle`。
- 不要在 `domain` 里 import LangChain。
- 不要在 CLI 命令里复制一套「加载 store → 两路检索 → 融合」；这是第 04 篇点名的重复点。
- 不要把 `Document` 当领域类型传遍全项目；它只应出现在 `retrieve/rerank.py` 的内部适配里。
