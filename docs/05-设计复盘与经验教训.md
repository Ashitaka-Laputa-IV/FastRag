# 05 · 放弃 FastRag：设计复盘与经验教训

> 代码基线：`dev@2d9604f`，版本 `0.2.0`。
>
> 这是这套文档的收尾篇。前四篇讲“它是什么、怎样运转、哪里可以改”；这一篇讲“为什么决定不再继续”，以及哪些设计判断值得带走。
>
> 这是一份项目所有者的决策记录，不是对代码价值的客观终审。放弃也不等于删除：代码、文档和数据产物仍然可以作为参考。

## 1. 先给结论

**FastRag 的问题不是“代码写得太差”，而是“这个项目不值得继续以通用库/产品的形态投入”。**

更准确地说：

- 微观设计合格：分层、领域类型、数据产物、失败降级都有可取之处；
- 宏观立项不成立：从仓库可见状态看，没有用户反馈记录和评测基线；从作者判断看，项目也缺少差异化，维护成本却会持续上升；
- 继续加功能，边际收益很低；继续重构，也只是让一个没有验证目标的系统更漂亮；
- 所以决定停止主动开发，把它归档为一个**已完成的学习项目/参考实现**。

第 04 篇的路线图原本是“若继续维护”的完整方案；本文改变了前提，决定不执行它。两者不矛盾：04 对代码质量和问题的评分仍然成立，05 只是在同一份评估上选择了退出。

## 2. “放弃”具体指什么

这里的放弃，指下面几件事：

- 不再增加新的检索、编排、CLI 或配置功能；
- 不再为了“以后可能用得上”而重构；
- 不再维护云端端点、索引数据和 API 费用；
- 保留仓库、文档和 tag，作为复盘材料；
- 如果未来有人接手，按“新项目”评估，而不是按“未完成产品”续命。

它不指：

- 否认代码能运行；
- 否认作者从中学到了东西；
- 否认某些模块可以被别的项目复用；
- 要求立刻删库或清空历史。

**停止投入是一个向前看的决定，不是对沉没成本的否定。**

## 3. 设计得好的地方

这一节不是客套。下面这些设计，即使项目停止，仍然值得保留或在下一个项目里复用。

### 3.1 范围克制：明确写出“不做什么”

`docs/01` 明确列了边界；README 则把项目定位为“本地文档混合检索问答”。具体边界包括：不做 Web 服务、不做多轮对话、不做多租户、不做 PDF/HTML 解析、不做 ANN、不做 agent 自主规划。

这很重要。很多个人项目死于“顺手再加一个功能”，而 FastRag 至少在一段时间内守住了边界：

- 单机、单用户；
- 只处理 Markdown；
- 固定四步 DAG；
- 几千到几万 chunk；
- 检索与回答是主路径，不是平台。

**做得好的一点，是把“不做什么”写进了文档，而不是只留在作者脑子里。** 这让项目在扩张时有一个可对照的边界。

### 3.2 单向依赖与薄 CLI

依赖方向基本保持为：

```text
cli → pipeline → index / retrieve / llm → ingest / config → domain / errors
```

这带来两个直接好处：

- CLI 只做参数解析、调用和打印，不承载业务逻辑；
- `domain` 不依赖 LangChain，`config` 不依赖 pipeline，下层可以被单独理解和替换。

对比“一个 `main.py` 里塞完下载、切块、检索、回答”的常见写法，这条依赖线是明显的工程优势。它让代码的阅读顺序和执行顺序大体一致。

### 3.3 领域类型不是装饰

`Chunk` 和 `ScoredChunk` 的设计很克制，但很有效：

- `Chunk` 携带 `source/start/end`，并附带默认值为 0 的 `token_count`，把“可追溯”变成类型的一部分；
- `ScoredChunk` 强制携带 `channel/rank`，融合层不需要猜结果来自 BM25 还是向量；
- LangChain 的 `Document` 只出现在 rerank 的内部适配里，没有污染 domain 和 pipeline。

很多 RAG 项目让 `Document` 贯穿全链路，最后 metadata 变成无类型的垃圾袋。FastRag 没有这样做，这是一个成熟的选择。

### 3.4 数据产物的完整性设计

这是项目最值得保留的部分：

- `chunks.jsonl` 是唯一真源；
- chunk id 内容寻址：`sha1(source + "\0" + text)[:16]`；
- 向量 manifest 记录模型、维度、ids 和来源 digest；
- BM25 meta 严格校验 digest 与索引参数；
- 单文件写入使用临时文件 + 原子替换；
- `prepare` 把切块、嵌入、索引串成可重复的流水线；
- 删除或修改语料后，向量可以按 chunk id 增量复用并补嵌缺失项；BM25 仍需要全量重建，两者都以 `chunks.jsonl` 为唯一源。

它解决的不是“怎么检索”，而是“怎么保证检索用的数据没有悄悄错位”。后一个问题通常更贵：线上答案变差时，你很难判断是索引对不上，还是模型变笨了。

需要补充的是，这种完整性是**单文件级**的，不是事务级：向量 npy 与 manifest 是两次写，BM25 目录由 `bm25s.save` 直接写入。项目没有把它包装成“整体原子”。

### 3.5 失败就地降级

三个关键降级点的语义很清楚：

| 失败点 | 降级 | 产品含义 |
| --- | --- | --- |
| 路由模型失败 | 用原问题检索两路 | 宁可多检，不放弃资料 |
| 重排服务失败 | 退回 RRF | 排序差一点，但结果仍可用 |
| 回答模型失败/空回答 | 按配置尝试 fallback；未配置则返回空回答 | 单轮失败不拖垮交互 |

`local` profile 默认没有配置 answer fallback，所以“尝试 fallback”只对配置了 fallback 的 profile 成立；未配置时，最终会得到空回答，但交互不会因此退出。

降级发生在离失败点最近的地方，而不是在最外层统一 `try`。这让每个降级都有明确边界，也让“哪些错误应该暴露、哪些可以退化”成为可讨论的问题。

### 3.6 配置严格且集中

- 单份 TOML，没有多份配置漂移；
- pydantic `extra="forbid"`，拼错键立即报错；
- endpoint 引用、fallback 链、权重、切块参数有交叉校验；
- `.env` 与配置加载分离，`load_config()` 不隐式读 `.env`；
- 云端与本地只是配置差异，不是两套代码。

这套设计让“配置错误尽早暴露”成为默认行为。对一个小型项目来说，严格配置比“灵活但到处是默认值”更容易维护。

### 3.7 懒加载与打包资源

`ResourceBundle` 的 `cached_property` 做到了：

- `import fastrag` 无 I/O；
- `RagPipeline.__init__` 无 I/O；
- 寒暄类问题不需要加载索引；
- 同一个 pipeline 复用资源；
- 测试可以注入替身；
- 包内配置与提示词通过 `importlib.resources` 读取，wheel 安装后仍可用；
- 用户可以用 `$FASTRAG_HOME` 覆盖提示词和配置。

这是“库”的写法，而不是“脚本”的写法。即使项目停止，这个资源装配模式仍然可以复用。

### 3.8 调试命令是产品的一部分

`search`、`rrf`、`rerank`、`embed` 这些命令，看起来像开发辅助，实际上是 RAG 项目最重要的可观测性：

- `search` 能单独看 BM25；
- `rrf` 能看两路融合后的名次；
- `rerank` 能看重排是否真的改变了排序；
- `embed --query` 能验证端点与维度。

很多 RAG 项目只有 `ask`，一旦答案不好，就无法判断是召回、融合还是生成的问题。FastRag 把这条调试链路保留下来，是一个很好的工程习惯。

### 3.9 中文优先的文档与提示词

README、docstring、CLI 输出、提示词都是中文；默认文档虽然是英文 LangChain 文档，但交互和解释是中文的。

这不只是“本地化”，而是降低了二次开发者的理解成本。对于学习型项目，文档本身就是产品的一部分。

### 3.10 代码量控制得还算克制

整个项目约 42 个 Python 文件、2600 多行（不含文档和生成物），核心链路可以在一个下午读完。

它没有为了“看起来工程化”引入：

- 向量数据库；
- 消息队列；
- Web 框架；
- 多租户抽象；
- 复杂的插件系统。

对一个小型 RAG 实现来说，这个体量是合适的。

## 4. 设计得不好的地方

下面这些不是“代码洁癖”清单，而是导致项目不值得继续的真实原因。04 已按 P0/P1/P2 列过大多数证据；本节按方向、验证、质量、工程、运维、接口、配置、文档八层重新归纳，重点说明它们为什么影响退出决定。

### 4.1 方向层：先造通用框架，后找具体问题

这是最根本的问题。

项目一开始的形态就是“通用 RAG 库 + CLI”：

- 支持云端和本地两套 profile；
- 支持 RRF 和 rerank 两种融合；
- 支持 BM25 和向量两路；
- 支持库、CLI、交互式问答三种入口；
- 配置项覆盖切块、嵌入、LLM、重排、检索、融合、下载。

这些能力单看都合理，合在一起就变成了一个**没有明确使用场景的平台**。而通用性是有成本的：

- 每增加一个配置维度，就多一组组合需要验证；
- 每增加一种入口，就多一套行为和错误处理；
- 每增加一种 profile，就多一套端点和模型差异；
- 没有真实用户时，这些组合的优先级只能靠猜。

更关键的是，hybrid RAG 本身已经不是差异化能力。BM25 + 向量 + RRF + rerank 是成熟且商品化的方案，LangChain、LlamaIndex、Haystack 以及各类向量数据库都能提供。**再写一个通用的混合检索库，很难构成“必须由这个项目存在”的理由。**

如果重来一次，应该先回答：

- 谁的文档？
- 他们现在怎么找答案？
- 现有工具哪里不够？
- 用什么指标证明这个项目更好？

而不是先回答：

- 要不要支持 rerank？
- 要不要做本地 profile？
- 要不要上 LangGraph？

### 4.2 验证层：没有测试、评测和 CI

这是最致命的工程问题。

项目没有 `tests/`、没有 CI、没有评测集，也没有 linter/formatter 配置。结果是：

- 任何重构都只能靠手跑命令；
- 数据产物、降级路径、配置校验这些“最容易静默坏”的地方没有回归保护；
- 检索质量变好还是变坏，无法量化；
- 第 04 篇提出的所有改进，本身也没有安全网。

对一个 RAG 项目来说，“能跑”只是最低要求。真正决定它有没有价值的是：

- 召回是否覆盖了该覆盖的文档；
- 融合是否把相关片段排到前面；
- 回答是否忠实于来源；
- 改动之后这些指标有没有退化。

没有评测集，这些问题只能靠感觉。**而在持续变更、又没有回归指标的情况下，靠感觉维护的检索系统往往会退化成“看起来能用”。**

### 4.3 质量层：检索与回答的核心指标没有被证明

具体表现：

- 没有 Recall@k、MRR、nDCG 等离线指标；
- 没有“每个来源最多 N 条”的多样性控制，相邻 chunk 可能重复占用上下文；
- 向量检索没有最低分阈值，不相关也会返回 top k；
- `context_chunks` 是条数，不是 token 预算，长 chunk 可能撑爆提示词；
- RRF 权重（`bm25=1.1`、`vector=1.0`）和候选数没有数据依据；
- 默认 BM25 的停用词和 tokenizer 更偏向英文，中文检索需要额外评估；
- 回答没有结构化引用，也没有程序化校验“每句话是否真的来自 source”；
- `sources` 是融合结果，可能多于模型实际读到的上下文。

这些问题不是“再加一个功能”能解决的，它们需要一个评测闭环。没有闭环，项目只能不断堆“可能有用”的旋钮。

### 4.4 工程层：同一职责多处实现，且存在静默失败

代码的字面克隆率不高，但语义重复存在：

| 职责 | 位置 | 代价 |
| --- | --- | --- |
| 原子写 | `ingest/artifacts.py` 的 json/npy、`chunker.write_chunks`、`download.download` | 改一处容易忘另一处 |
| 提示词渲染 | `llm.prompts.render`、`pipeline.nodes._render` | 行为可能分叉 |
| 提示词名单 | `prompts.REQUIRED`、`resources.PROMPT_NAMES` | 名单不一致时难发现 |
| 检索编排 | `nodes.retrieve_* / fuse`、`cli/commands/rrf.py` | CLI 与图的行为可能漂移 |
| fallback 链遍历 | `config/models.py` 的 route/answer 两段循环 | 新增角色容易漏改 |

更麻烦的是静默失败：

- `Template.safe_substitute` 会把拼错的 `$questoin` 原样发给模型，而不是报错；
- `_answer_text` 捕获所有异常并返回空串，真实错误可能被 fallback 掩盖；
- `stream()` 压掉了 Pydantic serializer 警告和“v3 streaming protocol experimental”警告。

这些选择在“先跑起来”的阶段可以理解，但长期维护时，它们会把问题从“立即报错”变成“答案变差，但不知道原因”。

### 4.5 依赖与运维层：没有为长期运行设计

- 运行时依赖大多是 `>=`，没有上限；
- 流式依赖 LangGraph 的实验性 v3 协议；
- 没有文件锁，多个 `prepare` 并发写同一目录有风险；
- 没有指标（延迟、token 数、成本、召回条数）和追踪 ID；
- BM25 每次 `prepare` 全量重建；
- 向量检索是 numpy 全量内积，十万级以上会开始变慢；
- 下载器硬编码 `base_url + "/oss/python/"`，换站点要改代码；
- 下载重试是线性 sleep，没有指数退避；
- `download` 只要有一个文件成功就返回 0，脚本可能误判。

单机、单用户、几千 chunk 时，这些都不是致命问题。但它们意味着：**项目没有为“长期、多人、规模化”留下运行条件。** 如果继续做，迟早要补；而补这些的成本，可能已经超过重写一个更窄的工具。

### 4.6 接口层：三种入口，反而模糊了产品

项目同时提供：

- Python 库：`ask`、`stream`、`RagPipeline`；
- CLI：`download/chunk/embed/index/prepare/search/rerank/rrf/ask`；
- 交互式问答：`fastrag ask`。

这三种入口的服务对象并不相同：

- 库用户想要稳定的 API、类型和错误语义；
- CLI 用户想要一条命令解决问题；
- 交互用户想要低延迟、可中断、可读的输出。

但项目没有明确“主入口”是哪一个。结果是：

- `ask` 只有交互模式，没有一次性调用和 `--json`；
- 流式 API 是实验性的；
- `AnswerResult` 和 `AnswerEvent` 两套返回形态并存；
- CLI 的调试命令比产品命令更完整。

这不是单个 API 的问题，而是**产品形态没有收敛**。一个项目可以同时是库和 CLI，但必须有一个是“主产品”，另一个是“薄封装”。

### 4.7 配置层：旋钮很多，但缺少“默认值也是产品决策”的意识

严格配置是优点，但配置项的数量和默认值暴露了另一个问题：

- `context_chunks` 受 `top_n` 截断，实际条数是 `min(context_chunks, top_n)`；
- `thinking=false` 通过 `extra_body.setdefault` 注入，`extra_body` 显式设置时以 `extra_body` 为准；
- 向量的 `source_digest` 记录在 manifest 里，但复用主要看 chunk id，digest 不是硬校验；
- RRF 权重和候选数是手写常量，没有评测依据。

这些不是文档没写清楚，而是**配置表面比实际可解释的能力更大**。用户会以为“调这个旋钮就能控制行为”，但其中一些旋钮的效果受其他层限制。

对一个小项目，最好的配置策略通常是：

- 少量、正交、有默认值的旋钮；
- 默认值由评测决定；
- 不把内部实现细节暴露成配置；
- 配置项的增加必须有明确的用户请求或实验证据。

### 4.8 文档层：文档可以让项目“看起来比实际更完整”

这套文档本身就是一个例子。

写完 01–04 之后，项目看起来非常完整：有定位、有心智模型、有代码漫游、有评价和路线图。但文档不能替代：

- 测试；
- 评测；
- 真实用户；
- 长期维护。

文档越完整，越容易产生“项目已经差不多完成了”的错觉。实际上，文档只是把设计讲清楚，并没有证明设计有效。

**这是一个很重要的教训：文档是放大器，不是验证器。**

## 5. 根本原因：不是技术失败，是项目选择失败

把上面的问题往下追，会得到五个根因。

### 5.1 从“我想学 RAG”出发，而不是从“谁的问题”出发

学习目标是合理的，但它不应该伪装成产品目标。

- 学习项目可以追求覆盖面：BM25、向量、RRF、rerank、LangGraph、流式、配置、CLI 都试一遍；
- 产品项目必须追求结果：谁的什么问题被解决了，成本是多少，效果如何证明。

FastRag 的很多设计是“学习项目”的优秀设计，但它同时用了“通用库”的叙事。两种目标混在一起，导致：

- 功能越来越多，但没有一个必须存在的理由；
- 架构越来越完整，但没有一个真实场景来检验；
- 文档越来越长，但用户是谁仍然不清楚。

### 5.2 没有从第一天建立评测

如果项目第一天就有 30 条问题和一个 Recall@5 脚本，后面的决策会完全不同：

- 哪些配置值得加，由指标决定；
- 哪些降级有意义，由失败案例决定；
- 哪些重构值得做，由回归风险决定；
- 项目是否继续，由“指标有没有变好”决定。

没有评测，项目就只能靠“代码看起来不错”来推进。这是很多个人项目的通病。

### 5.3 通用性优先于垂直切片

通用库需要支持很多组合，垂直工具只需要把一个场景做到足够好。

FastRag 选择了前者：

- 两套 profile；
- 两种融合；
- 三种入口；
- 大量配置。

但真正能证明价值的，往往是一个很窄的垂直切片：

> 给定一份中文 API 文档，开发者用自然语言提问，系统返回带出处的答案，Top-5 召回率达到某个阈值。

这个切片不需要两套 profile，也不需要三种入口。它只需要一个能测的指标和一个真实用户。

### 5.4 复杂度增长快于验证能力

项目的复杂度主要来自：

- 增量向量；
- manifest/digest；
- 多级 fallback；
- 路由降级；
- 重排降级；
- 本地/云端双 profile；
- 多种 CLI 命令；
- 严格配置和交叉校验。

这些复杂度单看都有理由，但它们是**在没有测试和评测的情况下**长出来的。结果就是：每一块都需要理解，但没有任何一块被证明“值得它的成本”。

### 5.5 单人项目没有维护预算

单人项目最容易低估的不是开发时间，而是：

- 依赖升级；
- 端点变更；
- 模型换代；
- 数据重建；
- 文档同步；
- 问题定位；
- 情绪成本。

一个项目只要有足够多的活动部件，就会持续产生维护请求。没有用户时，这些请求来自你自己；有用户时，它们会变成压力。FastRag 的部件数量，已经超过了一个“随时可以放下”的小项目。

## 6. 经验和教训

下面按决策顺序归纳为七条。每条都对应前面的具体问题，尽量写成可执行的判断，而不是口号。

### 6.1 先有评测，再有架构

评测不是“项目做完之后的验收”，而是设计工具。

- 它强迫你说清楚“好”的定义；
- 它让配置和重构有方向；
- 它让“要不要继续”变成可讨论的问题，而不是情绪决定。

最小可行的评测不需要很复杂：20–30 条真实问题、一个 Recall@5/MRR 脚本、一份人工忠实度检查表，就足够开始。

这也是为什么停止条件要提前写：多长时间没有真实用户、哪些指标没有改善、维护时间超过多少就停止。停止条件不是诅咒项目，而是保护你的时间。

### 6.2 先做垂直切片，复杂度由需求支付

第一个版本应该窄到可以在一周内验证：

- 一份语料；
- 一个入口；
- 一条检索链路；
- 一个回答格式；
- 一个指标。

只有当这个切片被证明有用，才值得加第二路召回、重排、fallback、增量索引和多 profile。

每一个“以后可能用得上”的抽象，都应该有明确的触发条件：

- 语料经常变 → 才需要增量；
- 数据规模到十万级 → 才需要 ANN；
- 重排真的提升指标 → 才需要 rerank；
- 多端点经常失败 → 才需要多级 fallback；
- 有多个真实调用方 → 才需要稳定库 API。

没有触发条件的复杂度，都是未来的维护债。

### 6.3 测试与失败分级是设计的一部分

至少要有三类测试：

- **不变量测试**：`text == original[start:end]`、chunk id 稳定性、manifest 匹配；
- **行为测试**：路由为 false 时不检索、重排失败降级 RRF、空回答在配置了 fallback 时触发 fallback；未配置 fallback 时返回空回答；
- **契约测试**：配置拼错键会报错、提示词缺变量会报错、CLI 退出码符合预期。

不需要追求覆盖率，但要让“最容易静默坏的地方”有回归保护。

失败也要分级。FastRag 的一个好设计是“就地降级”，但它也暴露了一个边界问题：

- 外部服务失败可以降级；
- 数据/索引错误必须暴露；
- 配置错误必须尽早失败；
- 提示词拼写错误不应该静默放过。

在写代码之前，先列出“哪些失败可以吞，哪些必须炸”。这张表比任何异常处理框架都重要。

### 6.4 依赖、警告和实验性 API 都要有边界

`>=` 不是“兼容更多版本”，而是“把未来的破坏留给未来的自己”。

至少要做到：

- 核心依赖有上限；
- 有 lockfile；
- CI 使用固定版本；
- 定期升级，而不是等到装不上再升。

压掉警告，等于把未来的不兼容藏起来。依赖实验性 API，等于把项目的稳定性交给上游的下一版。

如果必须用实验性 API：

- 固定版本上限；
- 加最小冒烟测试；
- 把警告收敛到具体模块；
- 在 README 里写明风险。

### 6.5 配置不是越多越好，文档不能替代验证

配置是产品决策的显性化。每加一个旋钮，都要回答：

- 谁会调它？
- 调了之后预期发生什么？
- 默认值凭什么？
- 有没有测试覆盖这个分支？

如果回答不了，就不要加。一个没有评测依据的配置项，比硬编码更危险，因为它会制造“可控”的错觉。

文档可以把设计讲清楚，但不能证明设计有效。

- 文档说“支持降级”，不等于降级路径被测过；
- 文档说“支持增量”，不等于增量在删除/重排/模型变化下都正确；
- 文档说“可扩展”，不等于规模真的测过。

**先有证据，再写解释。** 否则文档会变成质量剧场。

### 6.6 买商品化能力，保留差异化

BM25、向量检索、RRF、rerank、LLM 调用、Web 框架、向量数据库，都是商品化能力。不要把“我会接这些”当成项目价值。

真正值得自己写的，通常是：

- 特定领域的语料处理；
- 特定任务的评测集；
- 特定工作流的交互；
- 特定约束下的成本/延迟优化；
- 别人不愿意维护的脏活。

如果一件事已经有成熟库，而你的实现没有明显更好的指标或体验，那就应该用库，而不是重写。

### 6.7 RAG 的信任问题，最终是引用和忠实度问题

召回率再高，如果回答不能追溯到来源，用户仍然不会信任。

一个可用的 RAG 系统至少要回答：

- 这句话来自哪个片段？
- 片段真的支持这句话吗？
- 没有资料时，系统会不会承认不知道？
- 资料里出现恶意指令时，系统会不会照做？

FastRag 的提示词写了“不要编造”，但没有程序化校验。这是“看起来正确”和“可验证正确”的差距。

## 7. 如果重来一次：一个更小的方案

如果今天重新做一个 RAG 项目，我会把第一版压到下面这个程度。

### 7.1 目标

> 给定一份 50–200 页的中文技术文档，开发者用自然语言提问，系统返回 3–5 条带出处的答案；Top-5 召回率达到预设阈值，回答忠实度经过人工抽检。

### 7.2 组成

- 一个 `ingest` 命令：Markdown → chunk；
- 一个索引：BM25 + 向量，先不做增量；
- 一个检索函数：两路召回 + RRF，先不做 rerank；
- 一个回答函数：固定提示词，要求输出 `[n]` 引用；
- 一个评测脚本：20–30 条问题，输出 Recall@5、MRR@5；
- 一个 CLI：`ingest`、`ask`、`eval`；
- 一份配置：只暴露语料路径、端点、top_k；
- 一套最小测试：不变量 + 关键降级 + 配置错误。

### 7.3 明确不做

- 不做多 profile；
- 不做 LangGraph（一个 30 行的顺序函数就够）；
- 不做 fallback 链；
- 不做增量向量；
- 不做 rerank；
- 不做交互式流式；
- 不做多种融合；
- 不做通用库 API。

### 7.4 何时再加

只有当评测证明需要时，才加下一层：

- Recall@5 不够 → 加 rerank 或改 chunk；
- 延迟太高 → 加缓存或 ANN；
- 语料经常变 → 加增量；
- 多端点不稳定 → 加 fallback；
- 有第二个调用方 → 再抽库 API。

**先证明有用，再证明优雅。**

## 8. 哪些资产值得带走

即使放弃项目，也不是所有东西都要扔掉。

### 8.1 值得保留

| 资产 | 原因 |
| --- | --- |
| chunk 偏移不变量 | `text == original[start:end]` 是可追溯性的基础 |
| `Chunk` / `ScoredChunk` | 领域类型清晰，换框架也能复用 |
| `ArtifactKey` / manifest 思路 | 数据产物需要来源指纹和参数记录 |
| 严格配置 + `.env` 分离 | 小项目也适用 |
| 懒加载资源装配 | 库化设计的好习惯 |
| 调试命令 | `search/rrf/rerank` 是 RAG 的可观测性 |
| 01–04 文档 | 可以作为 RAG 教学材料 |
| 失败分级表 | “可降级/必须暴露”比代码更持久 |

### 8.2 不要带走

| 资产 | 原因 |
| --- | --- |
| 通用库 + 多入口的野心 | 没有用户时只会增加维护面 |
| 双 profile / 多融合 / 多级 fallback | 除非有明确场景，否则是复杂度 |
| 未经验证的默认权重 | 没有评测依据的“调参” |
| 实验性流式封装 | 上游一变就可能坏 |
| 为了完整性保留的死代码 | 会让读者误以为还有另一条路径 |
| “文档很完整”的错觉 | 文档不是验证 |

### 8.3 如果有人接手

建议按这个顺序，而不是直接加功能：

1. 先打 tag，固定当前行为；
2. 加最小测试和 20–30 条评测集；
3. 锁定依赖版本；
4. 删死代码，收敛重复实现；
5. 只保留一个主入口；
6. 再决定要不要继续。

如果第 2 步做不完，说明这个项目还不具备继续维护的条件。

## 9. 退役清单

如果决定正式停止，可以按下面清单收尾。

### 9.1 代码与仓库

- 给当前版本打 tag，例如 `v0.2.0-final`；
- 在 README 顶部加一句“已归档，不再维护”，说明替代方案或“仅供参考”；
- 保留 `docs/01`–`05`，它们是项目最有价值的产出；
- 如果公开仓库，考虑在 GitHub 上 archive，避免新的 issue/PR 预期；
- 不要在没有测试的情况下做最后一次大重构。

### 9.2 数据与密钥

- 停止定时任务和 API 调用；
- 轮换或吊销云端 API key；
- 确认 `.env` 没有被提交；
- 决定是否保留 `data/` 产物；它们通常可以重建，不必进版本库；
- 如果数据包含敏感内容，按所在环境的要求清理。

### 9.3 文档与交接

- 在 README 或 docs 中写明“为什么停止”；
- 记录已知问题和不建议使用的场景；
- 保留评测思路，即使评测集没有真正建立；
- 如果未来有人接手，要求他先读 04 和 05，再决定是否继续。

### 9.4 心理上的收尾

- 承认“能跑”不等于“值得继续”；
- 承认已经投入的时间不会因为继续投入而变成正确；
- 把项目当作一次完成的练习，而不是一个失败的产品；
- 把注意力转到下一个有明确用户和度量的问题上。

## 10. 一页决策记录

```text
ADR-007：停止 FastRag 的主动开发

状态：Accepted
日期：2026-11-18
基线：dev@2d9604f / v0.2.0

背景：
- 项目已具备完整的 RAG 链路、CLI、配置和数据产物设计；
- 但没有测试、评测、CI，也没有可见的用户反馈记录或反馈闭环；
- 继续增加功能或重构，无法证明对用户价值有提升；
- 维护成本（依赖、端点、模型、数据）持续存在。

决定：
- 停止新增功能和主动维护；
- 保留代码、文档和 tag 作为参考；
- 不把项目继续包装成“即将可用”的产品；
- 如未来重启，按新项目重新评估，而不是按未完成项目续命。

后果：
- 若有现有用户/调用方，需要自行 fork 或迁移；
- 云端端点与数据不再保证可用；
- 文档成为主要遗留资产；
- 作者的时间转向新的、有明确用户和度量的问题。

重启条件（必须同时满足）：
- 有一个明确的使用场景和至少一个真实用户；
- 有一个 20–30 条问题的评测集和可重复指标；
- 有稳定的维护预算；
- 能说清楚“为什么不用现成方案”。
```

## 11. 结语

FastRag 不是一无是处。它把一个小型 RAG 的**数据边界、失败边界和配置边界**讲清楚了，也留下了一套可以阅读、可以拆解的代码。

但它也证明了一件事：

> **工程质量好，不等于项目值得继续。**

一个项目可以分层清楚、类型干净、文档完整，同时没有可见的用户反馈、没有评测、没有差异化。继续投入，只会让沉没成本变大。

所以，放弃它不是一个草率的决定，而是把“我已经写了这么多”换成“我接下来要把时间放在哪里”。

它完成了自己的使命：让作者真正理解 RAG 的工程结构，也让后来的人可以沿着 01–04 走一遍，再沿着 05 看到它的终点。

这比继续维护一个没有验证目标的框架，更有价值。
