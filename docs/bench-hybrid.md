# 混合链路基准：本地规划 + 云端回答 + 本地嵌入

- 日期：2026-10-27
- 分支：`bench`
- 配置：`config/fastrag.hybrid.toml`
- 数据：`data/bench/results-2026-10-27-hybrid-run1.json`、`...-run2.json`
- 日志：`data/bench/bench-run-20261027-hybrid-run1.log`、`...-run2.log`
- 口径：到首 token（拿到首 token 即断开），远端回答模型**关闭思考**

## 0. 摘要

- 两次独立执行，端到端中位数 **1988 ms / 1599 ms**；18 次合并中位数 **1940 ms**，P90 **2657 ms**。
- 构成（18 次合并中位数）：检索规划 **~781 ms（40%）**、首 token **~1122 ms（58%）**、召回 **~33 ms（1.7%）**、融合 0.1 ms。
- 本地规划非常稳：18 次全部落在 **694–896 ms**（标准差 51–73 ms）；本地嵌入召回 **25–42 ms**。
- 远端回答有明显尾延迟：18 次里有 **2 次**首 token 超过 8 s（8.5 s、13.7 s），把均值从 986 ms 拉到 2567 ms（run1）/ 1659 ms（run2）；中位数不受影响。
- 相比云端全远程的 7496 ms，混合链路中位数快 **3.8 倍**；相比全本地的 2508 ms，快约 **1.3 倍**。

## 1. 配置

| 角色 | 选择 | 理由 |
| --- | --- | --- |
| 检索规划 | 本地 `qwen3-4b-instruct`，关思考 | 规划只要判断 + 两条查询；本地中位数约 0.8 s，且不受公网抖动影响 |
| 回答 | SiliconFlow `deepseek-ai/DeepSeek-V4.1-Flash`，**`thinking = false`** | 直接测模型首 token 411 ms，是云端第二快档；回答质量已有历史基线 |
| 嵌入 | 本地 `bge-m3`（1024 维） | 向量召回约 30 ms；复用 `data/embeddings-bge-m3/`，不重新嵌入 |
| 融合 | `rrf`，`k = 60`，权重 `[1.1, 1.0]` | 与其它配置一致，0.1 ms |

- 语料仍是 2625 个 chunk，BM25 索引、切块与 `top_n = 5` 均未改动。
- 本地服务：`bge-m3` 在 `127.0.0.1:9931`，`qwen3-4b-instruct` 在 `127.0.0.1:9938`。
- 回答模型的思考已显式关闭（配置 `thinking = false`，bench 默认也不传开启参数），远端请求带 `enable_thinking = false`。

## 2. 方法

- 两次独立执行，每次 3 个问题 × 3 次 + 1 次预热（预热不计入统计）。
- 直连 `api.siliconflow.cn`，运行时清空代理变量；本地模型走 localhost。
- 阶段耗时由 `timed` 装饰器记录；「首 token」是 `answer` 节点从发请求到第一个文本 chunk 的时间。
- 命令：

```bash
env -u ALL_PROXY -u all_proxy -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
  uv run python -m fastrag.bench --config config/fastrag.hybrid.toml --runs 3
```

### 3.3 尾延迟

18 次运行的首 token 排序后：

| 指标 | 首 token | 端到端 |
| --- | ---: | ---: |
| 中位数 | 1122 ms | 1940 ms |
| P90 | 1881 ms | 2657 ms |
| 最大值 | 13754 ms | 14678 ms |
| 超过 3 s 的次数 | 2 / 18 | 2 / 18 |
| 剔除 2 次离群后的中位数 / 均值 | 991 / 986 | 1848 / 1811 |

- run1 的离群：Q1 第 3 次，首 token 13.8 s，端到端 14.7 s。
- run2 的离群：Q3 第 2 次，首 token 8.5 s，端到端 9.2 s。
- 两次离群都发生在**远端回答**，本地规划与检索在同样两次里仍是 0.7–0.9 s / 30–37 ms，说明抖动来自公网模型服务，不是链路本身。

## 4. 与其它配置对比

| 阶段 | 云端全远程 | 全本地 | 混合（本文） |
| --- | ---: | ---: | ---: |
| 检索规划 | 6936.6 | 1083.6 | **780.5** |
| 召回 | 141.6 | 41.5 | **32.5** |
| 融合 | 0.1 | 0.1 | 0.1 |
| 首 token | 491.0 | 1453.9 | 1122.3 |
| **端到端中位数** | **7496.4** | **2508.4** | **1940.1** |
| 端到端最大值 | 14536.0 | 2908.5 | 14678.0 |

- 云端/全本地数据来自 [`bench-first-token.md`](bench-first-token.md) 与 [`bench-all-local.md`](bench-all-local.md)；口径相同（到首 token、思考关闭）。
- 混合链路把「最慢的一环」（远程规划，6.9 s）换成本地 0.8 s，端到端因此快 3.8 倍。
- 首 token 比纯云端配置的 491 ms 慢，原因有两个：本地规划生成的查询不同，导致送入回答的上下文不同；远端服务本身也有波动。18 次里 16 次落在 0.41–1.88 s。
- 全本地的首 token 更慢（1.45 s），因为 4B 模型处理 3–4k token 上下文；混合把这一环交给云端，正好互补。

## 5. 结论与建议

1. **混合链路是目前最优的默认方案**：中位数 1.6–2.0 s，比云端全远程快约 3.8 倍，比全本地快约 1.3 倍，同时保留云端回答的质量。
2. **本地规划可以放心用**：18 次规划全部在 0.69–0.90 s，抖动只有几十毫秒；它是链路里最稳定的部分。
3. **远端回答是唯一的不稳定源**：约 11% 的请求首 token 超过 8 s。如果对尾延迟敏感：
   - 给回答节点加超时（例如 3 s）并在超时后回退到本地 `qwen3-4b-instruct` 或另一个云端模型；
   - 或者直接改用首 token 更稳的模型（Hunyuan-A13B 230 ms、Qwen3-30B-A3B 254 ms，见 [`llm-ttft.md`](llm-ttft.md)），但需要先做回答质量抽检；
   - 或者对延迟极敏感时用全本地（无尾延迟，但首 token 1.45 s）。
4. **不要把首 token 中位数当作 SLA**：本次均值和 P90 都比中位数高不少；报告里应同时给出 P90。

## 7. 局限

- 每次只有 3 个样本，两次合计 18 次；尾部结论（2 次 >8 s）样本量小，只能说明存在明显的长尾。
- 只测到首 token，没有评估回答质量、完整生成耗时与幻觉率。
- 本地规划是 4B 模型，查询质量与 DeepSeek 规划不同；本文没有对比两者对召回质量的影响。
- 本地嵌入 `bge-m3` 与云端 2560 维嵌入的检索质量没有量化对比。
- 远端模型服务在时段上的负载差异很大；换时间复测可能得到不同的尾延迟分布。
